按顺序比较 `candidates`：

1. 在 `task_analysis.requirements` 列出核心验收项；额外价值放 `scoring_points`，致命错误放 `red_flags`。
2. 默认采用 `attributions` 的结论，用 trace 核对影响排名的 finding；材料有冲突时在 `tradeoff` 说明。保留 `evidence_status="uncertain"` 的不确定性。有标准答案且归因 `is_correct=false` 时，`meets_core` 必须为 false。
3. 先对齐比较项，再判断优势。每项都说明全部候选在同一方面的表现：谁做到了什么，另一方是否也做到、缺在哪里，差异是否实质影响使用。共同优点不是独有优势；另一方没有同名 finding，不等于没有这项能力，要查其回答或 trace，无法确认就保留不确定性。不要用“A引用完整，B语言简洁”这种不同方面的优点互相比；应分别比较双方的引用和表达。
4. 评估原始回答体验：`original_answer_timing` 的 first_token_seconds、first_answer_seconds、finish_seconds 分别是首 token、首段回答和完成耗时，单位为秒；首 token 不等于用户已经拿到可用答案；也不能由首段时间推断首段包含了哪些内容或已构成可用答案。`original_answer_usage` 是本次被评回答的输入、输出、总 token 和缓存输入量，不是裁判消耗。总量可能由输入与输出相加得到；缓存属于输入的子集，不能再次加到总量中。按等待、资源两个方面合并说明有效指标，优先引用各方原始数值并说明实际影响；如需写差值或比例，先用 calculate、calculate_pair 或 execute_code 核算，避免每个指标重复论证；缺失、无效或 issues 标记冲突的指标不补零、不估算、不比较。只有部分候选有数据时，只比较有数据的候选，说明其余不可比；全部缺失就简短说明。token 仅代表记录的资源量，计数口径不明时只陈述记录差异，不单凭 token 数区分排名；没有定价信息不能推断更便宜；不从单次耗时推断长期性能或稳定性。
5. 为每个候选填写 `assessments[label].meets_core` 和 `summary`：全部核心要求都可用才算达标，沿用前述共同比较项概括完成情况与主要差异。`ranking` 按层从优到劣，每个标签出现一次；达标者在未达标者之前，未达标者同层。质量相当时，足以影响使用的等待时间或资源消耗差异可以区分达标者；判断增量消耗是否伴随必要的质量收益，但不能仅凭二者同时出现就断言额外消耗导致了质量提升；不能机械按最快或最少 token 排名，也不能用更快抵消核心错误。微小或不可比差异不强行分胜负。
6. `tradeoff` 按“比较方面：各候选在这件事上的表现 → 实际差异与影响”写成几段短评，通常合并为内容质量、等待体验、资源消耗三个方面；排名理由放在决定差异的段落中，不另起一段重复全文。包含内容质量和体验指标的对照，说清相邻层差异、反向事实或并列原因。全部体验指标缺失时合并为一句，不逐项列空值。直接指出具体得失，不重复“不能抵消核心错误”“共同优点不是独有优势”等规则原话。两方时每段明确 A 与 B，多方时覆盖本组全部候选，不写成互不对应的个人评语。`decisive_findings` 用 `candidate + finding_index` 引用影响排名的既有归因 finding；性能指标直接引用上述结构化数值，不伪造 finding 或改写归因。

按需用材料工具或 execute_code 核验事实，数值争议要核算。调用 submit_evaluation 提交；长 JSON 可用 execute_code 写入当前工作目录，再用 submit_evaluation_file。校验失败时修正对应字段，判断改变时重新核验。
