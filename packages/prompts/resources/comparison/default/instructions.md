比较本题全部候选：

1. 在 `task_analysis.requirements` 列出核心验收项；额外价值放 `scoring_points`，致命错误放 `red_flags`。
2. 默认采用 `attributions` 的结论，用 trace 核对影响排名的 finding；材料有冲突时在 `tradeoff` 说明。保留 `evidence_status="uncertain"` 的不确定性。有标准答案且归因 `is_correct=false` 时，`meets_core` 必须为 false。
3. 逐条处理 `strength_checks`：根据 `candidate + finding_index` 找到一方的既有优点，逐一核对 `counterparts` 在同一件事上是否做到。对方也做到就是共同优点；只做到一部分就写具体差距；确认没做到就明确写成对方的相对短板，并说明影响；材料不足则保留未知。双方方向都检查，多方时检查其余全部候选。缺少同名 finding 不等于没做到，须查看最终回答或相关 trace。同一方面的重复优点合并，独立优点不能漏掉或只罗列在各自 summary 中。相对短板写在对比点评，不新增归因 finding，不把可选加分项缺失升级为核心错误。
4. 逐项对齐写入 `decision_basis.comparisons`，一行只比较同一件事：`aspect` 写具体方面，`assessments` 包含全部候选，每格用一句短句写做到什么或缺少什么，`finding_indices` 只关联本候选已有的归因。必须覆盖全部 strength_checks、归因中所有中高重要性问题和 decisive_findings；同一方面可合并多个 finding，反向优势也独立对齐。确证的相对优势填 `better_candidates`；共同优点、相当或无法确认优势时填 []，未知在对应格说明。对方没有同名 finding 时先核对回答，不能直接判缺失。`importance` 按该方面对任务的实际影响填写，核心差异优先，轻微瑕疵靠后。不按缺点条数判输赢，不为赢家删缺点、为输家凑缺点，也不把同一问题拆成多条。

`tradeoff` 只写裁决短评：先说谁更好或并列，再用最关键的一至两项差异说明原因，通常两句、40—80字，最多160字。逐项细节留在 comparisons，不在这里重述各人的优缺点清单。只留决定性差异，共同做对的内容不重复；工具名称清单压成具体比较项（如“对冲方案比较”），删去“能帮助用户形成风险清单”“难以同等支持选择”等抽象影响，直接说缺了什么。赢家有更多轻微问题时，直接点明它赢在什么关键结果，不能按数量反推输赢。不会改变排名的局部瑕疵留在对应比较行，不在裁决末尾追加“但也有不足”“仍需注意”式尾巴；确实影响取舍的反向优势不能隐去，先交代取舍，最后明确裁决。各候选 summary 一句说清主要表现，最多160字。

缺链接、脚注编号错位、引用格式或来源展示不完整，默认是 low 的核验便利性/格式问题，不能单凭这些判核心未完成或决定输赢，更不能把“没有展示来源”推成“事实错误”。只有伪造来源、来源与关键结论矛盾等有证据且实质影响核心事实时才提高重要性；用户明确要求可追溯来源时评估具体未交付内容，避免夸大为答案全错。
5. 读完内容质量再判断回答体验：同样好但等得更久，说明额外等待没带来实际收益；更慢且结果更差，点明花了更多时间仍未做好；更慢但补齐了重要结果，说明这些收益是否值得等待。若速度与质量各有得失，直说取舍；同时出现更多耗时和更好结果，不等于已证明前者导致后者。没有实质体验差异就不凑点评，数据缺失只在影响该判断时说明无法比较。不要固定列“首 token / 首段 / 完成 / 输入 / 输出 / 总量 / 缓存”，也不要强行分成内容、耗时、资源三段。通常只引用支撑体验结论的一组完成耗时；其他数据仅在改变判断时引用。token 是内部资源量，不等于用户等待或费用，不单独为了展示数据写一段；确有明显浪费且有可比依据时，结合未获得的质量收益说清楚。
6. 指标口径：`original_answer_timing` 的 first_token_seconds、first_answer_seconds、finish_seconds 分别是首 token、首段回答和完成耗时，单位为秒；首 token 不等于可用答案，也不能从首段时间推断首段内容。`original_answer_usage` 来自被评回答，不是裁判消耗；缓存属于输入子集，不能再加到总量。缺失、无效或 issues 标记冲突的指标不补零、不估算；仅比较有效且口径可比的记录，计数口径不明时不单凭 token 排名，无定价不能推断更便宜，单次耗时不代表长期性能。优先引用原值，如需差值或比例，先用 calculate、calculate_pair 或 execute_code 核算。
7. 为每个候选填写 `assessments[label].meets_core` 和 `summary`。`ranking` 分层，每个标签出现一次，核心达标者在未达标者之前，未达标者同层；局部差异在点评中说明。质量相当时明显的等待差异可以决定体验优劣，更快不能抵消核心错误；差异很小或无法可靠比较时并列。把排名理由放在决定差异的短评里，不另抄一段规则。`decisive_findings` 只用 `candidate + finding_index` 引用影响排名的既有归因 finding；体验判断使用原始指标，不伪造 finding。

表达示例（仅示范写法，不能当作本题事实）：
- 裁决短评：A更好。A把债务成本与对冲方案讲清楚了，B只说明汇兑方向，缺少可执行的方案比较。
- 逐项对齐「对冲方案」：A格写“比较了远期、期权和债务币种置换”；B格写“只提到人民币融资，没有比较对冲方案”。
- 来源展示：A 有原始公告链接，B 未附链接；只影响复查便利性，不能据此判 B 数值错误。
- 日期口径：A、B 都写明统计日期，这是共同优点。
- 回答体验：两方结果和依据相当，A 用 8 秒完成，B 用 40 秒；B 多等的时间没有换来更好的答案，A 的体验更好。
- 回答体验：B 等了 40 秒仍把核心数值答错，A 用 8 秒答对；B 既慢又错。

按需用材料工具或 execute_code 核验事实，数值争议要核算。调用 submit_evaluation 提交；长 JSON 可用 execute_code 写入当前工作目录，再用 submit_evaluation_file。校验失败时修正对应字段，判断改变时重新核验。
