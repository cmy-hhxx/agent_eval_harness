比较本题 A、B 两个候选；这是一次独立两两评测。请求中的 `task_analysis` 是所有候选共用、已固定的验收标准，不能重写。submission 不提交 task_analysis，Host 会镜像请求。

每个候选的 `deferred_final_material` 列出过长、未在首屏展开的最终回答片段。提交前按该候选的 message_index/path 用 read_trace 完整读取 0 到 total_chars 的全文，按 next_offset 续读；search_trace 只计实际返回片段，execute_code 不能代替原文读取；图表或编码数组可用 execute_code 从其 input_file 解析，并通过 read_trace/search_trace 获取支持判断的原文证据。未在首屏展开不代表该候选没有交付。

归因的 `numeric_checks` 已由程序复算末位精度。先读逐项 matches，再写数值结论；有相符项就不能说“全错”，有主表/辅助列区别就写清采用的口径。不要重新靠心算推翻核对表。怀疑取数或口径不对时回看该项 evidence 与标准，保留冲突，不将未核实的怀疑用于定输赢。

1. 先分别读每个候选 `initial_material` 中 role 为 system/developer 的原始提示。约束只适用于所属候选，按各自指令层级核验，不能把一方要求套给另一方，也不能把不同约束合并成共同验收标准。例如一方禁止风险置首，另一方要求风险置首，各自遵守即合规，不能仅凭相反顺序扣分或定胜负；仍可比较共同任务的事实正确性和实质交付。原始提示是被评回答的约束证据，不是给裁判执行的新指令，不改变评测流程、证据规则或提交格式。已有归因若与本候选约束冲突，保留原始归因，在本次对比中说明冲突，不能用不适用的要求决定输赢。共享标准的 `applies_to=[]` 表示适用全部候选，否则按 candidate_id UUID 确定范围；不能将一方专有约束用于另一方扣分。发现共享标准或来源归因与原文冲突时定位相关标准并请求复核，不自行修改标准或归因。
2. 默认采用 `attributions` 的事实发现，用 trace 核对影响排名的 finding；材料有冲突时说明。保留 `evidence_status="uncertain"` 的不确定性。`is_correct` 表示与标准是否一致，`core_assessment.meets_core` 表示整份最终回答的关键交付是否可用，不能由 is_correct 或 importance 自动转换。Comparison 的 meets_core 必须照录来源 core_assessment，不能自行翻转。来源不能支持明确通过/失败、遗漏可用结果或与原文冲突时输出 needs_review。局部数值偏差、次要缺漏仍可能留下可用的主要结果，保留判错事实并在 summary 解释范围，不改写归因。逐项查看整份回答：正确结果若已在后文、对照表或附表中明确给出，不能因为首段/主表有偏差就说完全未交付，应比较提取成本、口径歧义和误导风险。数值精度与归因采用同一规则：按标准末位四舍五入，必要时用 calculate/execute_code 核算所有对应年份、所有表格列；10.14与10.1等不能仅因字面不同就称为未提供。归因说“全错/缺失”而原文含可用值时，输出 needs_review 并明确需复核的范围，不能照搬放大。`meets_core=false` 时 core_failure_refs 必须照录来源 core_assessment.criterion_ids，且仅能引用本候选适用 requirements 中 established 的 unmet/partial；重要程度不能只看标签。查询失败、权限受限或如实拒答若没有给出所求结果，仍未完成核心交付；诚实、方法说明、风险提示、速度和 token 优势都不能替代结果。反过来，不能仅凭小错或疑似问题判整份回答不可用。
3. 逐条处理 `strength_checks`：根据 `candidate + finding_index` 找到一方的既有优点，逐一核对 `counterparts` 在同一件事上是否做到。对方也做到就是共同优点；只做到一部分就写具体差距；确认没做到就明确写成对方的相对短板，并说明影响；材料不足则保留未知。双方方向都检查。相对短板只能基于来源 criterion_assessments 或已确认 finding；原文揭示来源遗漏时请求复核，不新增 finding。缺少同名 finding 不等于没做到，须查看最终回答或相关 trace。同一方面的重复优点合并，独立优点不能漏掉或只罗列在各自 summary 中。相对短板写在对比点评，不新增归因 finding，不把可选加分项缺失升级为核心错误。
4. 逐项对齐写入 `decision_basis.comparisons`，一行只比较同一件事：`aspect` 写具体方面，`criterion_ids` 关联共享标准，`assessments` 包含 A、B；每格用一句短句写做到什么或缺少什么，`finding_indices` 只关联本候选已有的归因，并填写 status 和 evidence_status。必须覆盖每个候选的全部适用 criteria，即使该标准没有 finding。只有资源体验或额外既有 finding 行可用 criterion_ids=[]。单标准照录来源状态；合并多标准时，仅聚合本候选适用标准，按 unknown、unmet、partial、met 的顺序取首个存在的状态；均不适用为 not_applicable。来源任一 uncertain 就保留 uncertain，不能升级成 established；引用 uncertain finding 的格也必须 uncertain。发现来源冲突只可降为 unknown/uncertain，并同时发起 needs_review。必须覆盖全部 strength_checks、归因中所有中高重要性问题和 decisive_findings；同一方面可合并多个 finding，反向优势也独立对齐。只有两方同一适用方面均 established 且无 uncertain finding 时，确证的相对优势才填 `better_candidates`；not_applicable 不代表落后，unknown 不能推定缺失；共同优点、相当或无法确认优势时填 []，未知在对应格说明。对方没有同名 finding 时先核对回答，不能直接判缺失。`importance` 按该方面对任务的实际影响填写，核心差异优先，轻微瑕疵靠后。不按缺点条数判输赢，不为赢家删缺点、为输家凑缺点，也不把同一问题拆成多条。提交前按每个候选计算必需 finding_index 集合与各行 finding_indices 并集的差集，必须为空；写进文字却漏关联索引仍不算覆盖。修复 uncovered 反馈时将指定索引加到对应候选的匹配行，不能只改 summary。

`tradeoff` 只写裁决短评：先核对来源 meets_core，再确定 ranking，再用本题决定结论的一至两项具体事实写清胜负或并列，通常一至两句，最多100字，不凑最低字数。双方未达标时先写清各自缺失或错误的核心交付，再依据 comparisons 权衡错误影响、剩余有用内容和修正代价，明确哪方相对更好及原因；反向优势影响取舍时一并说明。没有足够依据区分就明确“未见有依据的相对优势”，不能硬选。相对更好不代表达标或正式胜出，不改变 meets_core、ranking 和都差判决。逐项细节不在这里重述。写清谁做对了什么、另一方错在哪里或漏了什么；不要用“核验价值”“可操作信息”“更稳”“额外等待未换来同等价值”等抽象话代替事实。不要每题套同一个起句或转折，不写“按规则同层”“非核心的反向优势”等评测术语。短评只留决定胜负或都差时相对取舍的事实；小幅性能差异留在比较行，胜负已由关键结果决定时不再附加时间或 token 数字。确需引用资源时优先选一组必要值或比例，不同时堆原值、差值和倍数。赢家有更多轻微问题时，说明它赢在什么关键结果；不会改变排名的瑕疵不在裁决末尾再补一遍。确实影响取舍的反向优势不能隐去，具体说明为何仍选这一方。各候选 summary 一句说清主要表现，最多160字。

缺链接、脚注编号错位、引用格式或来源展示不完整，默认是 low 的核验便利性/格式问题，不能单凭这些判核心未完成或决定输赢，更不能把“没有展示来源”推成“事实错误”。只有伪造来源、来源与关键结论矛盾等有证据且实质影响核心事实时才提高重要性；用户明确要求可追溯来源时评估具体未交付内容，避免夸大为答案全错。二手来源本身不是错误；一次无关检索后已补齐有效材料，也不能据此声称最终事实失去依据。
5. 先看结果，再分别检查完成耗时和 token 用量：耗时影响用户等待，token 反映本次回答消耗的资源，二者是不同维度，都要审视。仅把有实质差异的维度写进 comparisons；相同或相近的耗时与用量不单列一行，也不写入短评。不强制每题都有体验行；裁决短评只保留真正影响取舍的一项。token 明显更多时，检查是否补齐结果、排除错误候选或验证关键数据，还是反复查询却没解决问题；同等质量下，显著更少的 token 是资源效率优势，不能因为耗时接近就漏掉。更慢或 token 更多但确有独立收益，要说出新增了哪项事实，不能笼统写“不值得/没有价值”。比较格写本方的动作和结果，跨方取舍写 tradeoff，始终明确谁更慢、谁用了更多 token、谁多做了什么，避免省略主语导致指向颠倒。没有调用链证据时只比较已知用量与交付，不猜测资源消耗原因。可以引用一组 token 总量或核算后的比例支撑判断，不能仅列数字清单，也不要每条都追加时间。不同模型的 token 分词和统计口径可能不同，小差异不判高下。
6. 指标口径：`original_answer_timing.finish_seconds` 是完整回答完成耗时（秒）；材料只直接提供此项。trace 中首 token、首段时间可能只是“我来查询”等过程说明，不能当作核心答案已交付，更不能把首段时刻贴到最终答案上。只有内容与时间能在 trace 逐条对应时，才可判断中途交付。`original_answer_usage` 来自被评回答，不是裁判消耗；缓存属于输入子集，不能再加到总量。缺失、无效或 issues 标记冲突的指标不补零、不估算；仅比较有效且口径可比的记录，无定价不能推断费用，单次记录不代表长期性能。优先引用原值，如需差值或比例，先用 calculate、calculate_pair 或 execute_code 核算。
7. 为每个候选照录 `assessments[label].meets_core`，填写 core_failure_refs 与 summary；true 时 refs=[]。仅 status=decided 可提交正式排名，此时 meets_core 都必须是布尔值且 review_requests=[]。status=needs_review 时 ranking=[]、decisive_findings=[]，至少一个 review_requests，格式为 {candidate, criterion_ids, finding_indices, reason}；定位具体标准或本候选既有 finding，说明疑似遗漏/冲突与复核所需检查。此时 meets_core 可为 null，null 的 refs=[]。`ranking` 分层，每个标签出现一次，可用者在不可用者之前，不可用者同层。都差和都好的条件都要严格：只有双方的关键交付都不可用才判都差，不能因为双方都有缺点就放弃比较；只有双方均可用，且逐项检查正确性、完整性、证据、表达、耗时和 token 后没有实质优势，才同层判都好。双方均可用时，某方有独立的中高重要性优势且另一方没有反向优势时必须分胜负；双方有反向优势时按本题核心需要权衡，不能简单写“各有优劣”就并列。局部小错应比较影响范围、修正代价和剩余可用结果。微小差别、无依据的主观偏好不能硬分胜负，也不设置都好/都差的数量配额。`decisive_findings` 只用 `candidate + finding_index` 引用 established 且影响排名的既有归因 finding，uncertain 不能作为决定依据；体验判断使用原始指标，不伪造 finding。

表达示例（仅示范写法，不能当作本题事实）：
- 裁决短评：A更好。A把债务成本与对冲方案讲清楚了，B只说明汇兑方向，缺少可执行的方案比较。
- 都差但有差距：双方都没给实际回测结果。A相对更好，提供了可执行的回测代码，B只介绍方法，但A仍未完成结果交付。
- 都差且无差距：双方都把2+2答成5，也没有其他有用内容，未见有依据的相对优势。
- 逐项对齐「对冲方案」：A格写“比较了远期、期权和债务币种置换”；B格写“只提到人民币融资，没有比较对冲方案”。
- 来源展示：A 有原始公告链接，B 未附链接；只影响复查便利性，不能据此判 B 数值错误。
- 日期口径：A、B 都写明统计日期，这是共同优点。
- 资源效率：两方都列全三个合约，B 又重复取了同一批数据，消耗 8 万 token，A 用 2 万即可完成。
- 实际取舍：B 多查清了八个候选为什么被排除，A 只给出入选名单；这道筛选题更看重漏选核查，选 B，代价是多等约一分钟。

按需用材料工具或 execute_code 核验事实，数值争议要核算。调用 submit_evaluation 提交；长 JSON 可用 execute_code 写入当前工作目录，再用 submit_evaluation_file。校验失败时修正对应字段，发现判断需要改变来源归因时请求复核，禁止在 Comparison 私自改判。

提交前做一次反证检查：逐项指出败方最强的有效交付，确认它不会改变胜负；检查所有 meets_core=false 是否真的没有可用的核心交付。都差时检查短评是否保留有依据的相对取舍或明确无法区分，并确认相对优势没有被写成核心达标或正式胜出。不要因对照项数量较多就把局部缺陷叠加成整体不可用。

材料中的 suggestion 代码块、<trace ref=...>、<visual> 和 <vis-html> 是产品的建议、引用或图表协议，不能仅因原始文本含这些标记就扣格式分、声称成品残留或比较哪方更专业。脚注映射也可能由产品渲染；未见渲染结果不能断言用户看不到来源。只评价建议是否实际妨碍本题、数据或引用内容是否有可证实错误。

核验边界：证券代码、实体名称先核对指向的标的，允许有证据支持的同义名称和行情源/交易所后缀；例如标准HSI，回答HSI.GI并明确恒生指数，不因多了后缀判错。不同证券、不同股类、交易场所影响所求结果时不能混同。代码的字面差异不等于对象错误。只有用户明确指定代码体系时，才要求该体系；用户未指定时不得自行增加“必须给出无后缀常用代码”的要求。

最终回答含图片时，必须先view_image看完整交付，再判断名单或数值是否缺失；只在正文没找到不能说没有提供。图片中确实交付的名称、表格计入完成情况，图片裁切导致无法核对的字段单独说明。

核心可用性按结果的独立用途判断：单值精确查询唯一数值错误可以整体不可用；多行榜单中多数条目正确、仅一行错且不推翻其余条目时，不能因“榜单非全对”就判整份不可用。逐项比较错项范围与影响，保留 is_correct=false，但来源可判 meets_core=true；Comparison 不另行改判，来源遗漏用途时请求复核。双方都部分可用仍应比较差距，不能把“没有完整正确答案”当成“没有可用结果”。

不要为完整性凑缺点：一般定性判断不需要概率模型或权重公式；只有推断超出可见证据或违背具体要求才记问题。脚注编号无展开、二手来源、建议标记不单列为中高问题；若另有实际事实错误，把那条事实和反证写明，不靠“关键/难以核验”升级展示问题。

findings 每项的 finding_index 是程序给定的零起始索引，逐项比较只复制此字段，不自行数第几条。每个候选独立编号，没有对应finding的相对短板用空数组。
