1. 逐项比较。
- 使用共同 `task_analysis` 和双方已接受的 Attribution 结果，沿用已有 findings 和核心状态。必要时读取原始回答，确认各项结果。只有已确认的差异可用于判优劣。
- 按 `comparison_slots` 的数量和顺序填写 `comparisons`。仅 `optional=true` 且无实质差异或无需展示的槽可填 null。
- 每槽填写双方 summary、差异的 importance 和 better_candidate。双方围绕同一方面各写一句：做了什么，缺了什么，产生什么影响。优势须有双方实际交付的具体差异支持。
- `scope=source_only` 只写本方合规，better_candidate 省略或填 null。`scope=pair` 从 `advantage_candidates` 选择已确认更好的一方，无已确认优势时省略或填 null。
- importance 衡量差异对使用的影响：high 影响核心结果或关键决策，medium 影响局部结果或带来实质核查、修正成本，low 影响轻微且不改变结果或决策。

2. 核对比较依据。
- 对齐对象、日期、单位和口径，合理解释按同一尺度比较。时间使用本方原始上下文，保留条件、例外及“或/且”。
- 标准中的补充统计、验算中间值和额外解释不是必答项；不能仅因更像隐藏标准就判更完整。正确回答无需解释隐藏标准为何出错。清楚标注的替代口径、扩展窗口与主结果分别比较，双方采用同一尺度。附加分析只有确实改善题目要求的结果或决策才构成优势。
- 需要补读时，用 `read_trace` 读全正文和来源，用 `view_image` 查看图片。检查来源是否支持回答的具体说法，引用格式按本方协议判断。
- `numeric_checks` 记录直接点值的算术比较：rounded 按标准末位精度舍入，exact 精确比较；matches 不是正确性或核心可用性结论。查看原条件、`correctness_reason` 和计算证据，沿用已核实的精度、单位、容差、区间与上下限判断，不把显示精度差异改写成答错。
- 已接受归因标记 `standard_conflict=true` 时，在相关点评和整场取舍中保留“标准答案待复核”及具体原因；其中 `is_correct=false` 只说明标准不符，不能单独作为回答错误或对方更好的依据。继续沿用各方已接受的核心状态和独立发现，不将一方标记推写为另一方已经核实，也不据此声称整题无法评测或已停止计分。
- 点评说明具体偏差及影响，沿用 Attribution 的归因、标准一致性与核心可用性结论。逐项点评、双方总评和取舍理由中，提及评测依据中的答案统一称“标准答案”，不写“标准结果”“导入结果”“导入标准”等替代称谓；有差异时写清“回答为X，标准答案为Y”。工具返回或其他参考材料保留真实身份。

3. 作出取舍。
- 核心可用者优先于不可用者；双方核心不可用时判都差，tradeoff 可说明剩余用途、修正成本和已确认的相对优劣。
- 双方核心可用时，以共同适用方面已确认的中高重要性单方优势决定偏好。仅一方有此优势时选该方；双方各有优势时按任务需要取舍；没有实质差距时 preference 省略或填 null。
- 资源槽按 `resource_metrics` 在双方各自 summary 同时写出完成耗时（秒）和总 token；缺失或异常的指标写明具体字段和原因，另一项照常比较。即使资源差异不改变胜负，也保留本行和两项数据。
- `comparable_metrics` 列出双方均有效、可直接比较的指标。总 token 直接上报与输入加输出是同一总量的两种取得方式，缓存字段名称、缓存缺失或总量取得方式不同均不构成口径冲突。总量异常以 `original_answer_usage.issues` 的具体记录说明；缓存量是输入子集，不重复相加。
- token 表示本次记录用量，耗时表示本次等待；用 `calculate/execute_code` 核算差值与比例，并核对比较方向和分母：A 比 B 多用 (A−B)/B，B 比 A 少用 (A−B)/A，不能互换百分比。耗时与 token 的优势相反时分别说明，结合实际交付判断资源取舍；资源数字不能替代结果质量，也不直接等同费用或长期性能。
- a_summary、b_summary 写各方做到了什么、漏了什么、哪些结果还没查证。tradeoff 用一至两句解释判决，保留落后方有意义的优势。提交前核对主要任务是否完成，以及落后方最好的部分。单方未关联观察留在本方总评。

4. 提交。
按 `submit_evaluation_file` 的 Schema 整理结果，用 `execute_code` 写成 JSON 文件，再用 `submit_evaluation_file` 提交。收到反馈后修改文件，成功写入再提交。
