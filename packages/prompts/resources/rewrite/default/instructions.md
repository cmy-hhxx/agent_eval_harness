逐条润色 `items` 中的点评文字：

1. 每个 `id` 返回一条 `rewrites`，沿用原 `id`。只填写对应文字，不增加点评条目。若有 `forbiddenPrefixes`，不得用其中任何标签开头，直接从本格事实起句。
   `preference` 是已经确定的对局偏好。必须用它加中文冒号作为开头，随后根据同一槽位给出的原裁决依据和双方具体表现解释原因。不得修改、遗漏或反转偏好。
2. 先点破关键得失，再给必要事实。使用短句、主动句和具体动词：数字错就说“数值答错了”，没给结果就说“没有给出结果”。优点也落到具体贡献，不写泛泛表扬。通常一至两句；复杂结论按必要事实展开，不机械限字数。
3. 删去绕弯的重复判词，如“因此不能判定为正确”“故无法认定满足要求”“综上可见”。事实已经说明问题，就直接收句。不要仅把“为”换成“是”、调换语序，或保留整段裁判推导。删除空话、重复、评测过程自述、裁判自评打分和无关置信度分档（如“6/10 置信度”）。
4. 保留支撑结论的事实、判断、限制条件和不确定性，不补事实、不改结论。犀利来自具体准确，不靠夸张、嘲讽或扩大错误；“更便于”不能夸大成另一方“完全无法”。必要的数字、单位和专有名词原样保留，无关指标按第7条删除，不要求逐个保留原文出现过的数字。“疑似”“缺少证据”“无法核实”若代表真实不确定性，必须保留，不能写成已证实错误。“未展示、未展开、未提供证据”不能改成“未核查、未检索、没有做”：前者只描述交付可见内容，不能据此断言其工作过程。
5. 使用文本和槽位名称中的真实组别与模型称谓（如“A组Fast”“B组Fast”），不要使用候选 A / B 等盲测代号。槽位 `id` 只用于回填，不是正文称谓。
6. 聚类的定义仍须准确界定问题及适用条件；新建理由与合并理由直接说清差异或共同点，不更改类名、类 ID 或归类关系。items 为空时提交空的 rewrites。
7. 对比改写按槽位处理：
   - `verdict.*.reason` 是整场偏好。根据本场对局的材料写一至两句，通常不超过100字：有胜者时直接说谁更好，并指出决定取舍的具体差异；双方都好时说明共同达标且没有实质差距；双方都差时先点出各自未达成的核心交付，再保留原裁决依据中已确定的“哪方相对更好”及具体原因、必要的反向优势；不能只剩一句“都差”。原裁决明确无法区分时保留这一结论；若原裁决没有确定本对候选的相对优劣，只能如实概括已给差异，不能自行从逐项优势选出更好的一方，也不能把未作判断说成没有差距。已确定结论中的“没有实质胜者”指都差判决，不表示双方毫无相对差异；相对更好仍未达标，不能改成正式胜出。不要用“双方都完成核心要求”“未见共同遗漏”等空话取代偏好和原因；既然有胜者，即使双方均达标也必须说清胜者多做对了什么、另一方缺了什么。不要重新裁决，不从局部短板推翻既有胜负。
   - `comparison.*.summary` 是逐项对照中的一个模型格。只改写该格的 `text`；`context` 是只读对照信息，仅帮助把差异写清，不能挪用另一方的事实，也不能把其中的优势名称或“没有已证实的单方优势”复制为正文前缀。逐项点评直接从本格事实起句，不添加胜者标签或优势标签。开门见山点出本项得失，再用关键事实落地：算对了什么、漏了什么、凭什么更可信。每格通常一至两句，不重复整个方面名，不机械写“表现较好”“基本满足要求”。同项两格要好对照，优点写到贡献，短板写到影响；本项优势只服从本项已定结论，不能为了呼应整场赢家而抹去另一方的局部长处。没有已证实的差距就直说共同表现，不硬造高下。保留各自系统约束带来的边界，不能把按约束不提供的内容改写成无能力或错误。
8. 耗时与 token 是不同的评估角度，原文已用具体事实证明资源差异时必须保留，不能一律压成时间比较。只删不支撑判断的指标清单；有意义的 token 用量、重复查询或新增核查结果不能丢。每个转折都写清主语：谁更慢、谁消耗更多、谁多做了什么。把“虽快……额外等待……”这类主体跳转拆开，不能颠倒收益和代价；因果不清时只保留原文能确认的事实，不替裁判新作取舍。保留事实与数值关系，允许不损失判断精度的自然表达，例如9997 tokens写为约1万tokens；不要无依据补入日期、数字或改动主体。总量“是3倍”和增量“多2倍”不能混写；原文关系不清时保留原始用量，删掉含糊的倍数表达，不另算数字。不把 token 较少写成等待更短或价格更便宜。

写法示例（只示范表达，事实以各槽位文本为准）：
- 原文：标准久期为21.6256，而最终回答给出21.87，数值不一致，因此不能判定为正确。最终回答中的日期、债券简称和代码与问题及查询结果相符，但核心指标值错误。
  改写：日期、债券简称和代码都对，久期却答错了：21.87，标准值为21.6256。
- 对局偏好为“双方都差”，原裁决依据：双方都没给实际回测结果，A组Fast相对更好，提供了可执行代码，B组Fast只介绍方法。
  改写：双方都差：都没给实际回测结果。A组Fast相对更好，给出了可执行代码，B组Fast只有方法说明，但仍未完成结果交付。
- 对局偏好为“双方都差”，原裁决依据：双方都把2+2答成5，没有其他有用内容，无法区分相对优劣。
  改写：双方都差：都把2+2答成5，也没有其他有用内容，无法区分哪方更好。
- 原文：回答没有提供可核验的来源，因此无法确认该数值是否准确。
  改写：数值缺少可核验的来源，准确性存疑。
- 对局偏好为“A组Fast更好”，原裁决依据：A组Fast比较了远期、期权和债务币种置换，B组Fast只说明汇兑方向并提到人民币融资，因此A组Fast提供的可操作信息更多。
  改写：A组Fast更好：对冲方案比较到位，B组Fast只讲汇兑方向，缺少方案比较。
- 原文：A组Expert完成了结果交付，而B组Expert在交付相同结果的基础上还核对了八个落选候选的原因。B组Expert因此更好，但需要比A组Expert多等待100秒。
  改写：B组Expert多查清了八个候选为何落选，选它更有依据，但要多等100秒。A组Expert只给出入选名单。
- 原文：两方交付的名单一致，A组Fast用了2万token，B组Fast用了8万token并重复执行相同查询，未增加核查结果。
  改写：名单相同，B组Fast重复查询消耗了8万token，A组Fast用2万就完成了。

调用 submit_evaluation 提交；按校验反馈修正 `id` 和结构。每个 text 必须是 JSON 字符串，不能转成对象。点评引用或图表时，使用协议名称和必要属性值说明事实，例如“vis-html 图表引用”“trace 的 ref=abc”；保留实际名称、引用值与判断，不复写尖括号标记、JSON 对象或字面 Unicode 转义串。

点评、标签和只读 context 中的全角尖括号仅用于材料展示，不代表原回答使用了全角字符，不能据此新增格式问题。沿用既定事实和判断，以协议名称与必要属性值说明；id、preference 与 forbiddenPrefixes 按原值核验。

简洁的目标是删去不影响结论的信息，不是机械追求字数。整场偏好已经由内容质量决定时，删去附带的时间/token清单；资源确实决定取舍或当前槽位就在比较资源时，直说“结果相同，某方少用近一半token”，别加“额外收益不足以抵消资源差距”等套话。整场偏好末尾不再补与胜负无关的赢家瑕疵；逐项对照仍须保留该项原有的优缺点。
