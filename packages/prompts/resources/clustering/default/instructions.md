按顺序处理 `items`，问题库是现象目录，观察中的归因与确定程度是本次归类的事实边界。

材料中的 O1、O2… 是观察编号，C1、C2… 是问题类编号，P1、P2… 是组件编号。只使用本次材料给出的短编号；程序映射和保存真实身份。

1. 每条 item 在 `assignments` 中出现一次。同一组件下先比较已有类的定义与边界，含义相同的不同说法归入已有 `class_id`；每次都检查本次涉及的近义类，不能等 `budget.consolidate=true` 才处理重复。组件别名视作同一组件，确定程度不单独成类。
2. 没有合适类且预算、出现次数允许时，填写 `new_classes`，在 assignment 的 `new_class_index` 选择该新类的数组位置（从 0 开始）：沿用已有组件名，写简短 `label` 和独立、具体的 `definition`。新类无需填写 key，关联名称由程序生成。同组件已有类时给出该组件最接近的 `closest_existing` 及实质差异 `novelty`；该组件没有已有类时可省略 `closest_existing`，程序填 null，不从其他组件借类比较。名称换词、同一缺陷的不同后果或同义描述不足以新建类。
3. 没有合适类且新增类/组件预算、总数上限或 `min_support` 阻止新建时，提交 `deferred_reason`，说明实际限制。该观察仍被保留，后续可明确重新归类；不能为了完成归类硬塞进不匹配的类。已有同名或别名类时应先核查并复用。
4. 同组件近义类用 `merges` 指定保留类 `into`、被合并类 `from` 及理由；合并不增加本次新增预算。`budget.consolidate=true` 时扩大检查到整个同组件目录。
5. 新类及需要组织的已有类可填写 `category_paths`：每类最多三条自由主题路径，每条最多三级，每级直接填写字符串，例如 `[["工具使用","工具输出误解"],["数值可靠性"]]`，不把层级写成 `{"item":"…"}` 等对象。每级填写简洁的单行纯文本名称，不含 ASCII 标记分隔符 `< > [ ] { }`、换行或控制字符；发现这类字符时，依据目录语义重新填写该层名称。同一类可在多个主题中展示，仍只有一个类身份。沿用现有主题措辞，只保留有用层级；不重复路径或在一条路径内重复层级。它们描述现象，不新增因果结论。需要明确修正已有类名称、定义或主题时，用 `class_updates` 指定活跃 C 编号、要修改的字段及 `reason`；保留原责任组件，不改变观察、样本证据或确定程度。合并后超过三条主题时，明确整理保留类的路径。

组织时可参考这些方向，并按实际现象归并或细分：指令/计划遵循（欠执行、过执行、领域或编排规则）；虚构、增删改无支持事实或遗漏；无效工具调用（格式、参数、Schema）；工具输出误解；意图与计划错位；意图欠明确；缺少支持意图的能力或工具；护栏或访问限制；API、连接等系统故障。这些是分析方向，不是固定类别。用户意图含糊、没有支持工具、正确执行护栏或权限限制本身不自动构成缺陷。结果偏差与责任组件分别保留；不能凭最终结果或目录名称推断模型、工具、护栏或系统的责任。

`established_count` / `uncertain_count` 和示例的 `evidence_status` 保留原确定程度。类定义不是事实证据；引用标识可映射到来源与来源支持所附主张分别核查，工具调用次数或标号大小不能证明引用错误。定义只描述可复用的行为、触发范围与可见结果，不新增观察未证明的成因、禁令或必需输出结构；不把一个样本的严重程度、核心是否可用或胜负固化为整类性质。字段或期间未对齐、内部不一致、缺少信息分别按实际现象描述，不能自动扩成术语替换、故意省略或系统失败。长期 label、definition 与主题只写可独立理解的现象及边界，不使用本次 O/C/P 临时编号解释含义；业务型号、错误码等真实文字按材料保留。

assignments.item_id 填 O 编号；class_id、closest_existing、merges.into/from、class_updates.class_id 填 C 编号。每条 assignment 在 class_id、new_class_index、deferred_reason 中选择一个；new_class_index 只选择本次 new_classes 的实际数组位置，多个观察可以选同一位置。组件填名称，不填 P 编号。编号仅在本次请求有效；调用 submit_evaluation 提交，按校验反馈修正完整结果。
