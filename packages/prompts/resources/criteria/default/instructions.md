1. 阅读 `source_catalog`，提取本轮适用的要求。`question` 是问题，`reference` 是标准答案，其余来源按完整上下文判断。检索结果、附件、NER 和历史问题作为材料。检查项中的数值、日期和阈值引用原文；需要推算的结果写成待核任务，交给归因阶段核验。
2. 将任务拆成可分别核验的交付项。每条填写 `source_indices` 和 `text`：选择目录中的来源编号，用一句话写清对象、所求结果和可观察的完成条件。可独立答错或遗漏的指标、交付物分别列项；验收条件相同的多个对象可成组，但须保留完整对象范围和逐一覆盖要求。同一来源可支持多项。
3. 保留时点、窗口、单位、阈值、或/且、触发条件和例外。先解释数字在完整句子中的作用，区分比较对象、数量边界、日期、代码与事件名称，再写验收条件；保留含义相同的表达，不把名称里的数字当作阈值。决定方案能否使用的时窗、禁令等必要限制单独列项，核查范围覆盖完整交付及后续步骤。原文允许缺数时说明缺口，就按该条件验收。
4. `requirements` 列必需项，`scoring_points` 列明确可选项，`red_flags` 列明确禁令，同一义务只记一次。“不必”表示免除义务。口径有歧义时，要求说明所用解释并保持计算一致，对所有候选采用同一尺度。没有对应项目的数组填 `[]`。
5. 每个 question 和 reference 来源至少支撑一条共同 requirement。同一交付的问题与标准答案合成一条，`source_indices` 同时选择两份来源。目录 `applies_to` 表示来源适用的候选位置，空数组表示全部；多份来源的作用域取交集。共同交付与候选私有要求分别列项。
6. 按任务实际涉及的内容自查覆盖：对象与名单范围；指标定义、单位与分母；时点、窗口和端点；筛选条件及逻辑关系；计算方法、精度和缺失值处理；所需事实、解释、建议和成品。把这些条件落实到对应交付项，明确核查什么结果及怎样算完成。题目明确要求来源、可复算过程或文件时单列检查；其余任务不额外添加固定格式、引用数量、研究深度或方法偏好。
7. 标准答案只约束它实际覆盖的结果。“包括”“例如”等部分列举不当作完整名单；题目要求的其余交付仍须覆盖。题问与标准的对象、期间或口径存在表面冲突时分别保留原文含义，将对齐写成待核动作，不把冲突条件合成已确认事实，也不要求回答复述隐藏标准。
8. 提交前逐句回看原问和适用上下文，逐项确认检查短句与所选原文语义一致：未遗漏条件，未新增必需步骤，未将待核解释或推算结果写成既定标准。同一缺陷不重复计入。三个数组合计最多24条；合并原文依据、作用域和验收条件相同的重复项，保留各独立检查点，避免为拆分对象用尽条目而漏掉关键条件。耗时和 token 由后续资源槽统一比较，不从题目外另造资源阈值。

通过 `submit_evaluation` 提交三个数组。每条只填来源编号和检查项文字，身份、完整原文与适用范围由程序绑定。
