1. 先明确 question 中的实际目标，用 context 解析指代和仍有效的用户要求，按各候选 instructions 的指令层级确定其约束。requirements 只列完成本题所必需的结果，每个候选至少有一条适用要求；共同任务目标通常用 applies_to=[]。scoring_points 只列有任务依据的可选加分项，red_flags 只列本题明确需要避免的错误；没有独立加分项或禁止事项时填 []。
2. 共同要求的 applies_to=[]。某候选特有的合法约束，只在 applies_to 中填写其 candidate_id 原值；候选的相反约束可分别成立，不能把一方要求施加给另一方，也不能将分别合规本身当作一方优势。candidate_id 是输入 UUID，仅用于明确作用域。
3. 每条判据只验收一项结果或一条约束；text 写要求，acceptance_rule 写如何判断满足，明确本题相关的对象、时间、指标口径、单位、交付和允许误差。只使用任务已有要求，不增加固定篇幅、引用数量、工具次数或自行设定的权重。重复要求合并，三数组合计最多 24 条。
4. 标准答案只供评测核对，不代表被评方知道它。ground_truth.available=true 时，按题目或标准明确给出的容差和区间核对；否则连续数值按标准展示的末位精度四舍五入，整数计数和日期核对其所指值与时点。“约/≈”不授权额外百分比容差。把标准用于界定应交付的结果，不添加“必须对照标准答案”等被评方无法执行的任务。任务本身有多个合法口径时保留它们，不能因标准仅展示一种口径就静默扩大限制。
5. 为每条判据分配 r1、s1、f1 等简短 ID，三数组内全局唯一；ID 是后续关联判据的标识，不是数组下标。保持同一判据的 ID 稳定，不因文字润色重新分配。task_type 和 goal 概括本题，不预判任何候选的实际表现。
6. 通过 submit_evaluation 或 submit_evaluation_file 提交规定结构。校验反馈指出 ID、作用域或数量错误时，只修复对应字段并检查关联判据。
