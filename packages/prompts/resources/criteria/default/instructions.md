1. 读题定目标。先读目录前部的共同来源，从 `question` 明确本题要交付什么、满足哪些条件，再结合相关用户 `context`。可独立遗漏或答错的交付分别列项，保留对象、时点、单位、范围、条件与例外。来源的 `applies_to` 显式列出适用候选位置，`source_index` 是提交时使用的编号，目录顺序不改变编号。
2. 先写共同必需项。`required_common_source_indices` 中的每个编号都须在适用于全部候选的 `requirements` 中出现。按 `question` 写任务交付，按 `quality` 写本题适用的质量检查；有 `reference` 时单独列共同正确性要求，写清原题所求结果、关键要点与口径，接受等价结果和表达。参考答案的背景、示例与附带过程不增加必答内容。共同项只选 `applies_to` 覆盖全部候选的来源，默认一项选一个直接依据；一个来源可拆成多个检查。实际对错和事实核验交给归因。
3. 再写本方业务约束。按各来源的适用候选分别提取相关 `instruction` 和用户 `context`，按指令层级、完整条件和例外判断效力。内容相近但适用候选不同的要求分别列行。每行的 `source_indices` 表示所选来源同时约束同一批候选，范围取交集：来源适用 [1] 和 [2] 时不能合并；共同来源与仅适用 [1] 的来源合并后只适用 [1]，不能覆盖共同必需项。确需合并时，先确认适用范围相同、描述同一验收点，再选择多个来源。
4. 核对并提交。每项 `text` 用短句写清怎样算做到，适用候选由所选来源确定，无须在 text 重述候选编号。检查每行来源有共同适用候选，再逐个核对必需的共同来源是否由共同 `requirements` 覆盖。私有来源只约束对应候选，检索材料、内部备注和已给事实不另增交付义务。合并重复检查，三个数组合计最多24条。

`requirements` 填必需项，`scoring_points` 填有依据的可选改进，`red_flags` 填明确禁令；没有项目填 `[]`。核验口径不等于要求回答另写解释，耗时和 token 由后续资源槽比较。通过 `submit_evaluation` 提交。
