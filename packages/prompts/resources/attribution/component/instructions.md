当前任务调查 investigated_components 这一组组件，程序已按调用链分组；每条问题用 actor_index 选择组内责任组件，不提交或改写组件名称。依据 user_requirements，按顺序逐次检查 invocations 配对的请求与回执，核对主体、期间、单位、字段及计算；结合 model_actions、callable_contracts、skill_evidence、tool_errors、context_invocations、final_claims 和 final_answer 判断修复与剩余影响。调用成功、有数据或终稿采用不代表业务正确。components_content 与 Compact 只作导航；partial 或关键实现未见时用 read_trace/search_trace 定点补读，不能把未核实写成正常。

提交 content、evidence、tool_error_reviews、problems，不增加其他字段。content 不超过600字，简述本组实际核对结果及未核实事项；每条 tool_error_reviews.content 同样不超过600字。每条问题写清责任组件有原文支持的动作、偏差及剩余影响或恢复经过，用 evidence.index 选择配对请求、结果及交付原文，并必须提交 tool_error_indices（无关联异常时填 []）。本组确认正常时返回 problems: []。组件只是执行入口或传播上游错误时，不承接上游责任，尤其不能把上游已偏离请求的结果再改称终稿新增错误。

对 tool_errors 中每条待核查异常恰好提交一个处置，原始错误编号由程序给出；upstream_error_context 是其他组的异常，仅用于判断传导，不在本组重复处置。处置五选一：unresolved_impact（未恢复且有剩余交付影响）、recovered_impact（已恢复但仍有交付影响）、recovered_no_impact（已恢复且无交付影响，必须选择报错后的实际工具回执）、no_delivery_impact（未恢复但交付不受影响）、uncertain（根因或影响不清楚，不关联问题）。recovered_no_impact 与 no_delivery_impact 都以 P4 记录过程缺陷，区别只在是否已有报错后的实际工具回执证明恢复；仅失败回执、计划或终稿自述不证明恢复。没有 tool_error 的 planning、request_generation 或 script 过程缺陷，只有已证实终稿未受影响时才能记 P4；问题的 evidence 必须包含终稿、替代来源或修正后的实际回执，写明终稿未采用、已替代或已修正。影响未确认、未核实或可能时不报 P4，不能把 P4 当兜底。所有描述使用简洁中文，真实名称与引文保留原样。
