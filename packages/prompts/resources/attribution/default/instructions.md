依据 `task_analysis` 评审本方 `answer`。先核查结果和必要限制，再写逐项状态、核心结论和问题归因。本方材料工具的 `candidate` 填 `answer`，参考材料使用 `reference_materials` 中各自的 key。

1. 读全材料，确定适用要求。
- 先用 `read_trace` 读完尚未展开的正文和图表数据；有图片时，用 `view_image` 查看。读完后再开始评审。
- 核对本方适用的 `requirements`、`scoring_points`、`red_flags` 及 `acceptance_rule`。按 `criterion_checks` 原顺序返回恰好 `criterion_check_count` 行，每行填写状态、证据状态、短评和 `evidence_indices`；条件未触发的条款也保留对应行。
- `acceptance_rule` 中的完整原题和适用来源决定验收含义；检查短句若有省略或新增义务，回到原文核查，不按短句加码。数字需先判断其角色，事件名、日期和代码中的数字不直接作为数量边界；严格与非严格不等式、区间端点、并且与或者按原条件分别核验。
- 指令遵循按本方的指令层级、完整条件、例外和可选性判断；长规范用 `read_trace` 读全。检索结果、附件、NER 和历史问题作为上下文数据。
- 先确认规则的触发场景，再核查执行。例如“选出未知标的”和“分析用户指定的固定名单”须按原规范区分；不把前者专属的展示限制套到后者。判定未用指定工具或技能前，配对读取请求与返回，检查脚本路径、参数及嵌套调用；shell、代码或代理是调用载体，外层工具名不同不等于没有调用指定入口。
- 将对象、期限、单位、阈值、或/且和禁行范围应用到全部实际建议与后续步骤。时间区间按原文核对起止、端点和例外；相对期限与具体日期分别核算。
- 有 `review_context.reasons` 时，先逐项核对所涉原句、实际执行和完整来源，记录证据支持的结果，再完成整体评审。

2. 核对事实和来源。
- 用真实返回和完整文本核验主张。判定缺项或缺来源前，先用 `search_trace` 搜索实体、数值和同口径指标，再读取命中上下文。
- 对齐实体、日期、单位、指标定义、分母、范围和期间，区分来源事实、计算结果与分析推断。题意有歧义时，检查解释是否合理、已说明且计算一致。
- 条件分支分别核验，保留“自然日/交易日”“主结果/扩展窗口”等标签；不同前提下的结果不能拼成同一口径的自相矛盾。只有混入主结果、未说明切换或分支内部错误时，才按具体影响记录问题。
- 用 `calculate/execute_code` 按回答实际数量和分母核算，保留原始算式、单位和计算结果。精度与容差有明确要求时遵从原要求；其余情形根据未舍入原值和任务用途判断展示值是否等价，不能通过二次舍入制造错误，也不能自行编造容差。近似值、区间中值与下界按原任务和来源判断。已核实的内部数值矛盾记为 correctness 问题。
- 名称和代码核对实际标的、市场与股类，接受有依据的别名、沿革和行情后缀。
- 时间取自本方原始上下文或用户指定时刻，有 UTC offset 才换算时区。区分事件时间与报道时间，核对事件是否在要求的窗口内发生或发酵。日历计算覆盖全部参与对象、业务类别、年份和排除条件，列出逐日依据。
- 判断未来数据或收盘数据泄漏时，核查字段含义、数据更新时间及当时可获得性；盘中当日 K 线的 close 可能是最新价，仅凭字段名与日期不能确认用了尚未发生的收盘价。
- `answer.table_check_results` 是逐行字面对照。对 `conflict/ambiguous` 继续核查别名、日期和加工过程，`unverified` 保留待核；补充对照时使用 `check_table`。
- 根据引用目录，用 `read_trace` 读全来源，检查它是否支持引用所在的句子；同组来源可以共同支持一句话。同一文档的多个片段算一份来源。引用格式按本方协议检查。
- `answer_generation` 是最后一次真实 `llm_turn` 的助手输出，`final_answer` 是采集文本。两者有差异时分别记录生成与采集情况。文件内容、生成状态和下载可达性按原环境证据分别核查。
- 引证具体数字、图表或协议标签时，确认它实际出现在哪一层、哪个字段和对象；工具加工表不能冒充最终原句，trace 引用不能说成 visual 图表。局部截图或预览缺行不能证明完整交互成品缺行；缺少成品证据时限定观察范围。

3. 写逐项结论和发现。
- `status=met/partial/unmet/unknown` 表示满足、部分满足、未满足、证据不足；`red_flags` 的 met 表示遵守禁令。条件已确认未触发时在 summary 说明，并继续检查同条其余条款；全部适用条款满足才填 met。是否触发尚不明确且无已确认缺口时填 unknown，对应 `evidence_status=uncertain`。
- `strengths` 和 `problems` 分别记录独立的优点和问题，同一错误及其后果合为一项。`text` 一句话写做对或做错的事，`reason` 写核查依据，问题的 `impact` 写哪个结果或决策受影响。查不到依据时写清缺少哪份材料、哪个数值或哪项记录。
- 每条 finding 用 `basis_index` 选择直接对应的任务要求或本方规范；无对应依据时填 null。`own_rule` 只用于本方指令遵循；规范未确认时填 null 并保留 uncertain。`dimension/stage` 按实际内容选择。
- `importance` 按实际影响填写：high 影响核心结果或关键决策，medium 影响局部结果或产生实质核查、修正成本，low 影响轻微且不改变结果或决策。已确认中高影响问题对应的 requirement 应为 partial/unmet；证据不足为 unknown/uncertain。轻微附属错误可与 met 共存。
- `stage=final_answer` 的 `evidence_indices` 可为空，`text` 须准确描述读完正文和图片后的发现。其他 stage 选择支持判断的本方执行或推理证据。

4. 判断核心可用性与标准一致性。
- `core_requirements` 选择 Schema 允许的共同 requirements 正整数编号，`core_reason` 写实际可用结果和必要限制。本方私有要求保留逐项结论。
- `meets_core=true`：已确认的 met/partial 交付能独立完成共同核心任务，所选要求没有已确认 unmet；`false`：已确认的 partial/unmet 缺口使核心任务失败；`null`：存在影响核心判断的 unknown/uncertain。核实数值、日期偏差及必要限制对核心交付的影响；等价的数值表达不记为错误，局部偏差不自动推导为整体不可用。
- 有标准答案时填写 `is_correct`、`correctness_reason`、`correctness_evidence_indices`；证据至少包含本方最终回答。标准一致性尚未核实时，`is_correct` 与 `meets_core` 均填 null，并关联 unknown/uncertain 的共同 requirement。已确认不符填 `is_correct=false`，再按实际影响判断核心可用性。
- 标准不符且已核实本方工具返回或独立来源支持回答值时，填 `standard_conflict=true`，在 `correctness_reason` 说明来源与口径；其余情况填 false。先读全涉及冲突的原始来源，核对对象、指标与期间；不能仅凭候选与标准不同宣称标准有误，也不能把隐藏标准的写法当成用户要求。仅由标准错误或已说明的合理口径造成的冲突不列为候选 problem，不影响正确交付的 meets_core；其他独立错误照常核查。无标准答案时省略该字段，固定填 `is_correct=null`、`correctness_reason=""`、`correctness_evidence_indices=[]`、`numeric_checks=[]`，事实与计算照常核查。
- `numeric_references` 是从标准提取的数值目录，不代表已确认的点值目标。先按完整原题和来源判断哪些是题目所求的同口径直接点值，再逐项填写 `numeric_checks`；不把标准的补充数字或未要求展示的中间计数记作缺项，也不因此判 is_correct=false。需要解释定义的百分比/百分点、显式容差或区间目标，以及须计算或解码的分数、名单、图表等表达，在 `correctness_reason` 记录原规则、实际交付、推导和结论，并关联证据。混合情形仍填写其余直接点值。
- 每条 `numeric_checks` 选择原 `reference_index`，`actual` 保留最终回答的实际数值，缺项填 null；大整数用十进制字符串。`scale` 是有依据的单位倍率字符串，同单位填 `"1"`；万、亿计数若已展开成基本单位，使用展开后的倍率。需额外条件的换算在理由中给出依据，不能为凑成相等而改倍率。不同量纲按任务解释，不能因数字相同认定正确。
- 数值表只记录算术观察：`rounded` 将 actual×scale 按标准末位精度舍入，`exact` 精确比较；程序生成的 `matches` 不决定整体正确性。根据任务选择核对方式，离散计数用 exact。展示精度、二次舍入、指标定义或单位含义影响结论时，`correctness_reason` 须写出原题要求、双方原值、计算过程和判定依据；既不能把 matches=false 自动判错，也不能无依据豁免真实差异。Unicode 负号与减号同义。
- `numeric_checks.evidence_index` 选择证据目录中的正整数编号。非 null 数值须引用包含原值的本方最终回答片段；null 引用可核查缺失范围的最终回答。必要时先读完整表格行。没有直接点值目标时填 `[]`；日期、代码和需解释的百分比/百分点口径按原任务核验。

5. 定位责任。
- 核对最终结果、真实返回、请求条件和脚本。错误请求、字段或期间选择、计算、误读和结果校验归模型，填 `model_responsible=true`。工具自身返回错误且传入结论时，用 `tool_evidence_indices` 选择该工具失误的证据；两者各有独立失误时同时选择。
- 已确认回答错误时，记录对应的取数、计算或结果校验问题，写清对象、指标、时点、实际值与标准值；没有工具自身错误证据时归模型的取数与结果校验逻辑。已查明错误来自标准时，直接说明标准错在何处，不要求候选预先发现隐藏标准的问题，不给返回正确数据的工具记责。其他尚未定位责任的问题填 `model_responsible=false`、`tool_evidence_indices=[]`，在 `reason` 写已查到的错误和缺少的记录。
- `label` 简短概括问题，`definition` 写具体行为、适用条件和结果；点评直接说明偏差及影响。所有点评字段提及评测依据中的答案时统一称“标准答案”，包括总评、正确性理由、问题描述、观察和影响；不写“标准结果”“导入结果”“导入标准”等替代称谓。有差异时写清“回答为X，标准答案为Y”及具体差异；工具返回和其他参考材料按真实身份称呼，不冒称标准答案。
- `reference_materials` 的原始工具返回、资料、时间戳和图片可用于核验事实，并保留真实来源。参考回答用于定位待查主张。本方规范、时钟、工具责任及正确性提交证据仍取自本方材料。
- 有 `review_context` 时可用 `table_resolutions`：`table_index` 选本方 `answer_table_index`，`row_index` 从0开始，引用最终行和全部既有来源行。`supported` 只解除 unverified，须有非代码工具的完整肯定对应声明；存在反证时一并核查。`conflict` 须有 established problem 和两侧原文，证据不足保留待核。

6. 提交。
逐条反查 problem：原文是否确有该主张、规则是否触发、例外是否适用、证据是否支持所述对象与阶段、影响是否足以支撑严重程度。仅坐标有效或读完材料不代表判断成立；删除没有实际依据的问题，保留真实错误。按 `submit_evaluation` 的 Schema 提交完整评审，附上引用和看图记录。总评概括完成情况、主要贡献和缺口。收到反馈后修正对应内容再提交。
