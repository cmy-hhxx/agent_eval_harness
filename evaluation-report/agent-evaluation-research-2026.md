> 数据获取时间：2026-10-13（Asia/Shanghai）
> 调研深度：深度研究，面向建设决策与领导汇报
> 业务场景：在现有 TypeScript Host + Pi / Prime 上，提升真实业务回答与 Agent 交付的评测可信度。

## 0. 执行摘要

**建议保留现有轻量底座，优先完成“人工校准 → 分层实验 → 问题回归”。** 我们已经具备共同判据、证据归因、匿名比较、待核、恢复与统计校准工具。要向公开先进方法靠拢，当前更重要的是产生可信的质量证据，并让真实问题进入修复与回归流程。这个判断基于本地实现与本轮工程资料，置信度高。

“达到业内已知开源顶峰”应作为建设目标，以同任务、同材料、同预算的对照实验和外部复核证明。当前不能给出行业分位或宣称超越标杆：几家材料的任务、人工标准和指标均不相同，也没有统一的行业平均。

| 领导需要判断的问题 | 本轮结论 | 建议决策 |
| --- | --- | --- |
| 是否需要换平台 | 现有 Host、Workflow、Agent、Data、Runtime 已能承载大部分优先改进 | 保留主链，外部工具先隔离小试 |
| 最先投什么 | 人工审定与代表性实验是可信度的关键缺口 | 先批准 8–12 周试点，指定工程与业务样本负责人 |
| 美团与字节学什么 | 美团：标准治理与样本闭环；字节：三层诊断与工具复算 | 每项方法映射到具体样本、动作与验收 |
| 如何证明进步 | 人工确认误判变化、配对实验、稳定性、成本和复发情况 | 每轮报告分母、范围、区间与已知失败 |

**当前证据范围。** 离线汇报保存 30 题、84 份回答、42 场对局，其中 37 场正式、5 场待核。独立实验是固定 6 题 × 3 轮，仅重跑 Comparison，冻结既有 Criteria / Attribution；同位重复与换位分别为 5/6 一致，Wilson 95% 区间均为 43.6%–97.0%。这不是人工准确率，不是全链路可靠性，也不代表总体业务分布。事实依据为 `evaluation-report/README.md`、案例与实验快照。

**美团精读：标准必须能执行、能校准、能回流。** 原文把业务与模型能力之间的任务指标作为桥梁，先通过专家独立评价对齐理解，再进行人机校准；把模糊要求拆成可核验项，保留未知并分析其原因。生产案例经过清洗、质检与归因进入闭环，长任务需要输入、预期行为和执行轨迹。对我们最直接的增量是运营已有人审和实验工具，而不是再造一个评分引擎。[1]

原子项尽量明确，与整题允许部分可用并不矛盾。我们应继续区分事实核验、核心交付与相对优劣；保留 partial、unknown、都好、都差与待核，避免按问题条数或对勾数投票。美团文章的高一致率是特定业务自报，未给出足以用于跨系统比较的样本构成和区间，本报告不复用为目标已达值。

**字节精读：先分层找到问题，再用证据验证。** 基础能力测选型，组件测定位，端到端测业务效果。深度分析采用 Critic 初评、Reflect 复查，并用 ReAct 编码复算；SQL 专域采用 Calcite / RelNode 等结构表示和匹配。它对我们的启发是把“哪个环节出了问题”从整体分数中分离，并优先为可计算事实提供可重复检查。[2][3]

现有归因、比较和独立核验与评测侧 Agent 化的方向相近；结构相似不能证明效果等价。是否增加异模型核验或 Reflect，要用同一人工保留集比较严重误判与增量成本。SQL 专域的复杂算法当前不值得直接引入。原文所谓“准确性”按其定义是错误检出精确率，不应与我们的重复一致率放在同一排名图。

**AWS 与千问的证据定位。** AWS 的不同案例提醒我们区分执行过程与最终任务状态，并明确执行监控不能包办内容体验评价。[4] 千问文章可用作指标维度和流程的概念检查表，本身没有提供可复现实证。[5] 阿里云官方协议明确列出 qianwenai.com 关联平台；主体关联已核实，文章的证据权重仍按其内容判断。[6]

**近六个月新增信息。** 美团 2026-08 实践、AgentRx 2026-08 论文更新、Who&When Pro 2026-10 更新值得跟进。[1][21][22] DeepEval 官方当前已有 TypeScript beta；页面未稳定标明发布日期，因此只记获取日，不擅称其在某月发布。[16] 旧材料仍可解释方法，但不计为近六个月动态。

### 1.3 政策监控方向

本节只识别与样本、模型网关和未来服务形态直接相关的要求与治理动作，不代替具体法律适用审查。

| 分组 | 官方依据与适用边界 | 对评测体系的动作 |
| --- | --- | --- |
| 🔴 红线：个人信息处理 | 《个人信息保护法》第六条的目的明确、最小必要，第五十一条的分类与保护措施；具体处理依据及跨境路径需结合数据流判断 [23] | 样本分级、必要脱敏；外部模型只发送必要材料；明确权限与保留期限 |
| 🟡 关注：是否对公众提供服务 | 生成式 AI 暂行办法第二条区分公众服务与未向公众提供服务的内部研发应用 [24] | 内部离线工具不自动等同公众服务；未来产品化时重新核查适用义务 |
| 🟡 关注：可信测量与反馈 | NIST AI 600-1 是自愿风险管理资料，不是中国法律或合规证书 [25] | 保留评测来源、人工复核与风险记录，明确无法测量的范围 |

国家法律、服务范围和国际自愿框架已经覆盖本阶段直接相关决策。地方政策、专项资金及更细分行业标准，需要在实际落地城市、业务主体与服务范围确定后补查；本报告不将其编成现成利好。

### 2.1 学术前沿与理论极限

| 论文 | 作者/机构与时间 | 核心贡献 | 工程转化与限制 |
| --- | --- | --- | --- |
| AgentRewardBench [20] | Xing Han Lù 等，McGill-NLP 项目；首发 2025-04-11，v2 2025-10-06 | 对 web Agent 轨迹上的程序/LLM 裁判进行独立检查 | 建立我们的裁判保留集，预计 2–4 周起步；网页任务结论不能直接外推本业务 |
| τ²-bench [19] | Victor Barres、Honghua Dong 等；2025-06-09 | 用户与 Agent 均可改变共享状态，用组合任务区分推理与协调 | 1–3 月试一个可重置工具场景；当前离线回答不应被冒充为环境执行成功率 |
| AgentRx [21] | Shraddha Barke 等，Microsoft Research；首发 2026-02-02，v2 2026-08-31 | 结合轨迹、约束检查日志和证据诊断失败；v2 为 170 条轨迹、11 个场景 | 4–8 周构建受控归因小集；旧博客 115 条与新版口径不同，不混用 |
| Who&When Pro [22] | Jiale Liu 等；首发 2026-07-10，v2 2026-10-09 | 重放成功前缀后注入故障，构建 12,326 条带标签轨迹，覆盖 3 类模态、26 个 benchmark | 1–3 月设计责任组件/步骤检查；人工注错不能代表自然多因失败 |

论文数字仅描述研究对象，不是我们的测量结果。转化周期是规划估计，不是作者承诺。为统一证据口径，本表链接到原始论文版本，不使用未核实的会议等级或引用数；引用量尚未在统一来源核实。

**理论上限。** 开放业务不存在已知统一最高分。质量受来源完整性、任务歧义、人工一致性和状态可观测性限制；抽样区间无法覆盖裁判系统性偏差。稳定地给出同一结论仍可能是稳定地判断错误。

| 实验 | 固定与改变 | 能回答的问题 | 不能外推的结论 |
| --- | --- | --- | --- |
| 比较阶段重复 | 冻结标准、归因与回答，只重跑比较 | 最后一环是否随机变化 | 上游是否正确、业务是否完成 |
| 真实换位 | 匿名材料整体交换后重跑裁判 | 位置变化是否关联结论翻转 | 单次分歧必由位置偏差导致 |
| 评测全链路重复 | 固定被评材料，重跑标准、归因与比较 | 整条评测链路的波动 | 被测 Agent 多次任务都能完成 |
| 被测 Agent 重复 | 固定任务、初态与预算，重新生成执行轨迹 | 多次任务成功情况 | 不能从重复裁判同份回答计算这种可靠性 |
| 人工校准与消融 | 人先审原始来源，再核对裁判；每次只改一个因素 | 与审定依据符合程度、局部机制收益 | 无争议真值或所有业务普遍有效 |

Anthropic 区分 pass@k（至少一次成功）与 pass^k（全部成功）；它们针对重复任务试次，不能由重判同一份回答推导。[7] 实验还应控制资源噪声和评测污染：公开演示、开发和保留验证集分开，保留集不参与调参。[8][9]

### 2.3 最佳架构与主要工程模块

**建议架构：业务样本 → 分层实验计划 → 现有评测链路 → 人工校准与统计 → 发布评审 → 失败回流。** 其中业务分层、人工校准运营、发布评审与回归关联是本阶段拟补齐能力；原有评测核心保持职责边界。

| 模块 | 已有实现与职责 | 最小增量 | 技术路线与边界 |
| --- | --- | --- | --- |
| 样本与输入 | Workflow 的 input / input-catalog 读取与选择 | 记录分层、授权、纳入理由；分开诊断、调优与保留集 | 保留 TypeScript、业务 ID/UUID 与来源引用，不复制原文到每个 run |
| 判据与评测 | Criteria → Attribution → Comparison | 只在实验证明具体错误后修规则 | Prompts 集中维护；影响判词必须更新 evaluatorVersion |
| 独立复核 | 可选核验另记发现，不覆盖原判 | 按严重性、分歧与未知路由人审或异模型抽查 | 同模型独立会话不保证误差独立；不以投票替代证据 |
| 统计与校准 | benchmark compare / summarize / gold-template / calibrate | 审定数据、切片报告；需要时增加配对差值统计 | 现有汇总区间不自动构成机制改善的因果证明 |
| 问题闭环 | Attribution 产问题，Clustering 管问题库 | 关联人工确认回归样本、修复责任人与复测结果 | Attribution 不读问题库、不建类；聚类不是因果证明 |
| Data 与 Runtime | 文件锁、日志、Worker、双 SDK 与恢复 | 按样本/阶段记录失效与成本，按实测瓶颈扩容 | 外部统计 Schema 冻结；新增研究指标放实验报告，不擅自扩字段 |

10 倍规模先测排队、模型限流、阶段瓶颈和 IO，利用既有并发能力；100 倍规模再据数据决定分布式存储与鉴权。当前可信单机 HTTP 不能通过暴露端口直接变成远程服务；工作目录也不是安全沙箱。只有业务需要执行不可信任务时，才专项建设隔离。现状依据：`docs/architecture.md`。

## 3. 综合分析

### 3.1 SWOT 分析

| 内外部维度 | 判断 | 决策含义 |
| --- | --- | --- |
| 优势 | 业务语义和证据链较深，轻量底座、恢复与模块边界已具备 | 在现有链路上投入验证，避免重复建设 |
| 短板 | 人工校准与代表性实验不足，局部稳定性不能外推整体 | 先验证评测器，再扩大自动化范围 |
| 机会 | 把最新公开方法转为适合本业务的小型可复核协议 | 形成高质量数据与缺陷回归资产 |
| 威胁 | 同源裁判偏差、评测污染、小样本过度解读与数据边界扩大 | 保留独立审定与验证集，显式记录未知和失效 |

### 3.2 机会窗口

当前最短路径是把已经实现的工具跑出可信证据。美团标准治理与字节分层诊断可以马上进入人工试点，Anthropic 的实验设计可以降低错误归因；近半年归因研究则为下一阶段验证 Attribution 提供方法。[1][2][7][21][22] 此判断置信度高，收益大小需本地试点测量。

### 3.3 风险提示

- ⚠️ 运行成功、结构通过、引用有效均不等于语义正确；18/18 完成只能说明这次运行完成。
- ⚠️ 增加同模型角色可能重复共同错误；异模型核验也必须经人工校准。
- ⚠️ 未知下降可能伴随误判上升；不能为提高覆盖率强制裁决。
- ⚠️ 公开题、调优题与保留集混用会高估效果；保留集不用于提示词调参。
- ⚠️ 稳定性、自报精确率、任务成功率与人工一致性分母不同，不能混成一个总榜。
- ⚠️ 当前历史案例保留 r151/r152 来源；r153 是既有提示词快照。冻结上游的比较实验不代表全链路 r153。

### 3.4 行动建议

以下为内部建设建议，不是行业标准；本次只改研究与展示，尚未实施这些评测改进。

| 阶段 | 动作与责任 | 验收证据 | 对应依据 |
| --- | --- | --- | --- |
| P0，第 1–4 周 | 业务专家与工程负责人先双标 30–50 题；原始材料盲审、分歧仲裁；拆调优与保留集 | 每题有纳入理由、来源、审定者和依据；报告人人分歧及人工基线 | 美团标准治理；现有 gold-template/calibrate |
| P0，第 5–8 周 | 按实测工时扩至 100–200 题；分别测组件与完整评测链路；单因素比较异模型核验/复算 | 分母、配对变化、严重误判、重复/换位、未知/失败、区间、费用和耗时 | 字节三层；Anthropic 方法与噪声；现有 compare/summarize |
| P1，第 9–12 周 | 责任人将高影响问题转回归引用，修复后用新 run 复测；补高频任务结果断言 | 原失败、新结果、复测结论；回归覆盖、复发与关闭时长；发布前评审 | 美团闭环；AWS 状态核验；既有问题库 |
| P1，3–12 月 | 视错误分布增加受控故障、轻量人审队列和一个必要的工具场景 | 归因定位准确性、真实重复成功、维护成本可核查 | AgentRx / Who&When Pro / τ²-bench |
| P2，1–2 年 | 在许可范围内扩分域和对外复核 | 可复现协议与同条件外部对照；已知失败透明 | 业务规模与外部复核需求 |

**门槛制定。** 第一轮人审基线后，结合严重错误代价确定容忍度，并在看改进结果前声明。受控严重反例可设“零漏过”的内部门槛，但有限样本零观测不代表总体风险为零；仍报告样本量与不确定性。100–200 题是起步规模，不是统计充分性保证。不以无来源的 90%/95% 作为“行业先进线”。

**固定六个汇报口径。** 人工一致性与逐类混淆；人工确认的严重误判；裁判重复/换位与 Agent 重复分列；未知/失败/缺失单列；同 case 配对改进及区间；被评系统/评测器各自的费用、耗时、人审时间。改善区间不支持结论时写“证据不足”。同题多场有关联，不能当独立样本扩充分母。汇总已有成簇区间，配对差值与发布统计按需要另做，不能声称已自动具备。

**一次只试一个新增工具。** promptfoo 或 DeepEval 先用同一人工集离线对照，证明减少误判或审阅工时、增量成本可接受后才引入。Inspect 与 AgentRx 当前借鉴方法；LangSmith 当前借鉴人审流程。无需为本轮改进部署完整新平台。

### 3.5 资源需求

建议 1 名工程负责人 × 8–12 周，业务专家合计约 0.3–0.5 人力当量参与试点，另安排争议裁决与安全/数据评审节点。这是资源预留建议，包含标准讨论与复核，不是承诺需要新增固定团队。

作为量级估算：120 题 × 2 人 × 每题 15–25 分钟，约 60–100 评审人时；争议处理另预留 10–20 小时。复杂数值、多轮与长证据任务可能明显更高。先用 30–50 题测实际工时，再定最终样本量与排期。

模型预算按“业务 case 数 × 每题阶段数 × 重复次数 × 观测单阶段费用”估算，补失败重试与复核比例。无可靠单价时只报告 token 与耗时，不硬换算货币；评测器和被评模型的成本分开。以试点实耗决定上限，必要时优先重跑高风险/高分歧样本，同时明确其不能代表总体。外部合作仅在需要额外领域审定或独立复核时引入。
