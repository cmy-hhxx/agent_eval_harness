# 自动评测流水线

[返回首页](../README.md) · [远程数据契约](handoff.md) · [评测运行与恢复](usage.md#运行与恢复)

`automations` 常驻监控远端，按日期流式下载四模型输入，驱动已有 Host 先固定共同标准，再完成归因、对比和改写。归因与对比的改写均强制开启；对比改写在同一个任务中覆盖最终偏好理由、双方整体总评与整场取舍（`rewrite.comparisonItems=true`）。逐格点评直接呈现本方已接受归因，资源记录由程序生成，两者均不进入改写槽位；上传校验与改写计划共用当前槽位要求。聚类与聚类改写不在自动化中执行；只有共同标准、归因、对比及其改写成功才算本轮评测完成，必需的整体总评或取舍改写缺失或失败不算完整交付。存在输入校验问题，或未达对应配对额度且仍有缺配对输入时显示 `waiting_inputs`；已达额度且计划任务全部完成时显示 `completed`，缺配对数仍单独保留。

操作入口：[启动](#启动)（会取数、调用模型并上传）→ [历史接管与更新](#历史接管与更新) → [调度与状态](#调度与状态) → [MongoDB 与统计日志交付](#mongodb-增量交付与每四小时日志)。只读检查使用 `npm run automations -- check`；若只需处理不确定的线上回执，先看[上传恢复](#mongodb-增量交付与每四小时日志)，不要盲目重复发送。

## 启动

先完成 README 的模型和依赖配置，并在 `config.ini` 的 `[environment]` 设置 `AUTOMATIONS_MONGODB_URI`（已有集合的应用连接串）；TLS 连接需要 CA 时设置 `AUTOMATIONS_MONGODB_TLS_CA_FILE` 为证书绝对路径。使用 SSH 隧道时，由部署环境维护隧道并让连接串指向本地映射端口。默认[配置](../configs/automations.json)依次加载 `configs/host.json`、`configs/local/models.json` 与 `configs/automations-host.json`，复用共享的阶段模型、预算、输出目录和问题库，并将自动化并发设为 4。密钥不进入 JSON 配置或状态文件。

自动化的渠道池在 `config.ini` 单独指定，各阶段的模型 ID、推理等级和 Token 参数仍由 Host 配置决定：

```ini
[automation]
channels = openai, evaluation-gateway
```

所有列出的渠道必须已配置且具有有效密钥。完整任务按渠道的 `traffic_weight` 加权轮转分配；原渠道设为 `6`、OpenAI 渠道设为 `4`，每十个新任务分别分配六个、四个，两渠道同时分担任务。比例按首次派发的任务数统计，每个任务的模型请求数和 Token 独立记录；同一任务的普通重试保持渠道。模型服务明确返回配额耗尽或余额不足时，将该渠道移出本次进程的可用池，并把当前任务转到剩余渠道；普通 429 限流、网络错误、超时和鉴权失败不会触发渠道切换。切换保留内容提交账本和已接受结果，不消耗传输重试次数，也不会因这一批额度错误触发阶段暂停；全部渠道耗尽后停止切换，按正常失败保护处理。各渠道应提供同一个模型 ID。

耗尽记录由本次自动化进程共享，后续日期跳过已耗尽渠道，重启自动化后恢复完整渠道池。切换记录写入现有 `log/runtime.log`（`model_channel_switched`）。省略 `[automation]` 时遵循各阶段原有渠道绑定；手动评测用 `--balance-channels` 启用同样的任务分流，Eris 仍按会话选择渠道。

```bash
bash automation.sh
```

根目录脚本每次启动都会重新构建当前应用（包含提示词与校验），自动准备依赖并在同一个前台进程启动流水线和只读看板，默认地址为 `http://127.0.0.1:4174`。终端会打印地址；`bash automation.sh --port 4180` 更换端口，`--config FILE` 指定流水线配置，`--debug` 显示准备过程输出。`bash automation.sh --help` 只显示用法，不安装或启动。端口被占用时直接退出，不开始评测。`Ctrl+C` 一起停止流水线和看板；再次运行脚本使用原有状态继续。评测器标识来自 `hostConfigs` 合并后的 `evaluatorVersion`（默认 `configs/host.json`）；更改评测器后需停止旧进程并重新运行脚本，运行中的 Host/Worker 不热更新。已接受任务保留原版本，未完成和新增任务使用新版本；以下直接调用 `npm run automations` 的命令使用现有构建，修改源码后先运行 `npm run build:app`。

只读看板显示取数、评测与改写、MongoDB 和日志四个通道，以及日期进度、时段完成量和交付回执。它不提供启动或重试入口；布局、分页与状态呈现见[看板规范](../apps/host/.impeccable/DESIGN.md)。

统计口径：

- 并发只计有活进程持锁的 run，显示执行任务数 / 当前 Host 上限；阶段任务数、输入条数和正式对比份数分别统计。等待重试不占执行槽位。
- 本地就绪按四模型分别核对条数及快照状态；总数相等不能代替模型分布一致，条数一致也不保证内容相同。
- 完成量按正式回执时间归入北京时间整小时，普通日期要求归因、对比及完整改写；显式接管日期保留原执行范围。
- 缓存命中率为 `cacheRead / (input + cacheRead + cacheWrite)`，包含已返回的失败尝试用量；全局先累加 Token 再计算。无输入 Token 与命中率为零分别显示。
- Mongo 当前交付量取每日期最后成功回执或只读核验记录，不累加各轮累计数；在途写入不算成功，核验时间不冒充上传时间。当前失败与待核实记录始终可查。
- 顶部运行概览不随表格筛选变化；断连保留最后快照并停止重试倒计时预测，停机显示启动后重试。统计日志独立展示，不按单个数据日期截断。

也可使用已有 CLI 独立检查或运行：

```bash
npm run automations -- check
npm run automations -- run
# 同时运行看板（automation.sh 的入口）
npm run automations -- run --dashboard --port 4174
```

`check` 只读检查远端和历史 run，不下载、不调用模型、不上报进度。`run` 持续运行，`Ctrl+C` / `SIGTERM` 停止监控与下载，等待 Host 保存任务进度后退出；再执行同一命令恢复。部署到常驻机器时，可让系统进程管理器运行这个前台命令并在异常退出后重启。

```bash
npm run automations -- status
npm run automations -- run --once
```

`status` 返回保存的状态与 `ownerAlive`，后者用于区分运行中和进程异常退出后遗留的 `running`。`--once` 发现一轮输入，下载并执行可运行日期各一次，不在本次命令内等待失败重试；它会调用模型。停机、连接失败和 Worker 最终计数缺失后，直接执行 `bash automation.sh` 即按检查点与退避时间自动恢复，不需要先运行 `retry`。`npm run automations -- retry --date YYYY-MM-DD` 仅用于修复持续的结构、证据或判决校验错误后，显式解除该日期的保护性暂停；执行前先停止流水线。该操作不删除结果，也不重做已接受任务。其他配置文件通过 `--config FILE` 指定，文件中的相对路径相对于配置文件。

## 历史接管与更新

默认监控从 `2026-10-14` 起的日期，不设结束日期。`fromDate / throughDate` 同时约束发现、启动恢复、下载、评测和 Mongo 交付；范围外的既有日期账本、源文件和正式结果保持原样，不补阶段、不补改写、不重传，显式 `retry` 也会拒绝。因此截至 `2026-10-13` 的批次（含待核和提交预算耗尽的终态）保留原状，不会因升级评测器再次运行，也不影响新日期的退出状态。看板与累计统计仍只读纳入历史数据；交付校验以各任务已接受收据声明的改写槽位为准，缺失或空文本仍拒绝，不强加后来新增的改写要求。

`completedDates` 默认为空，范围内日期按正常流程评测。需要沿用范围内既有 `daily-<日期>` 交付时，在 `completedDates` 明确指定日期：先核对本地 `state.json` 的所有计划任务均成功且有收据，并核对输入索引各模型条数与远端一致，才登记为 `adopted`。这些日期在条数不变时不下载、不补阶段、不重新评测；因此它们保留当时的阶段范围，包括当时的改写范围。若条数有变化，转入普通下载和同 run ID 续跑。

每个日期只使用一个 `daily-<日期>` run，Fast 与 Expert 的输入、任务和结果都在其中。既有 run 只登记 Fast 时，自动化在原 run 内补充 Expert 两模型和相关归因、对比及其改写任务，保留 Fast 的已接受任务 ID 与收据；不会创建带模型后缀的目录。已接受的聚类结果、改写和问题库保留；续跑不安排新的聚类，未完成的聚类及其改写从本轮执行计划移出，仅涉及这些任务的暂停不再阻塞评测。普通自动化日期若只完成了偏好改写，续跑自动补齐缺失的整体总评与取舍改写，保留源评测和已有文案；完成后合并回原 JSONL。补写会解除 Mongo 同步进度的复用，确保即使对比数量不变也重新核对并上传新增文案。既有 run 的固定修复任务范围在全量续跑时释放；有限抽样或 case 选择的 run 会明确报错，不静默视为全日期覆盖。

普通日期每 15 秒读取 `/dashboard-data`，四模型都 ready 才接收。每次启动先读取新目录；日期暂时不 ready 时不使用旧目录状态发起下载，已有完整本地输入保留。目录检查与下载之间若遇到 `404: data not ready`，显示“远端准备中”，等待下一次目录轮询；远端恢复 ready 后自动继续下载，不将这一准备状态作为红色网络错误。条数变化立即进入下载队列；条数不变时，北京时间当天及前两天按 `refreshMs`（默认 30 分钟）流式复查完整文件；更早的日期若计划任务全部完成且没有输入校验问题，改为每 24 小时复查（配置的间隔更长时沿用更长值）。未完成日期保持原频率，下载失败仍按退避时间重试。复查逐块比较实际字节，覆盖同条数内容修正，不计算哈希；历史同量修正最长可能延后一轮每日复查才发现。未变化文件不替换，也不重新执行 Host。已接受结论遵守项目原有续跑规则：输入修正不撤销旧判词，只有新增或未完成任务使用当前材料。

远端没有 HEAD、ETag、修改时间或不可变快照 ID；当前协议无法保证下载的四文件来自同一服务端生成时刻。流水线校验每个响应的字节数、JSONL 结构、行数，并在下载结束再次核对目录条数；可见变化会重试。需要严格跨文件快照一致性时，远端必须提供生成 ID 和对应的不可变下载入口。

## 后置聚类

自动化固定关闭 `clustering.enabled`，不启动聚类或聚类改写。操作者可选择一个或多个已结束归因的日期 run，用 `cluster --run PATH ... --run-id ID` 预览，加 `--apply` 启动独立聚类作业；同一作业 ID 支持续跑。它按模型汇总跨日期问题，不改变原评测、改写或上传状态，也不进入自动化重试池。读取期间来源状态变化会明确报错，稍后重试；无需为已稳定的日期停止其他日期的自动化。命令见[后置聚类](usage.md#可选复核与后置聚类)。

## 调度与状态

自动评测按数据日期限量：`configs/automations.json` 的 `dailyComparisonLimitPerTier=300` 表示每个日期 Fast、Expert 各最多 300 次 A/B 对战，合计最多 600 次，两档不互借额度。一次对战包含原有归因、对比及改写流程，不按回答条数或模型调用次数计数。先保留已完成对战，再保留已选入的未完成对战，最后用新对战补足额度；重试、重启、输入追加或重排不会重置额度。已完成结果全部保留，历史某档已达到或超过 300 次时不再增加该档对战，降低上限不会撤销已接受结果。超额输入继续完整下载并保留在数据源，不进入自动评测，也不在次日补评；手动 Host 运行不受此限额影响。

远端看板的进度上报也按同一限额筛选，即使某日期尚未轮到 Host 整理旧任务计划，超额对战也不计入排队或失败。已完成数和未配对数保留实际值；已达上限且范围内无运行、排队或失败的配对显示已完成，不必等待其他日期评测结束。

任务检查点的 `nextRetryAt` 保存 Host 内部已安排重试的绝对时间；退避任务回到待调度池，立即释放 Worker 和并发槽位供其他健康任务使用，到期后重新竞争空闲槽位。单任务的传输／内容重试预算保留，不因重新入队重置；等待重试不算正在评测，也不重复计入普通待执行。重试开始、停止或恢复时清除该时间。看板只读取这一时间，不另行推算或调度任务。

流水线有下载、评测、MongoDB 同步和日志交付四个通道：评测某日时，可以下载其他日期并上传已完成结果；有数量差额的日期优先于同量周期核对，同类候选先处理最久未核对的日期，避免早期日期反复占用下载通道。已有完整本地快照的未完成任务可继续评测，不因远端出现新增输入而整体等待；如果下载通道空闲，仍先下载已就绪的新输入，再评测该日。下载某日时可评测其他日期的本地积压。同一天评测或 Mongo 交付期间只记录远端变化，延后替换该日源文件。日内任务并发由 Host 的 `execution.concurrency` 控制，默认值见[自动化 Host 配置](../configs/automations-host.json)。四个通道独立于目录轮询；两种上传互不等待，上传失败不消耗评测重试次数。全局日志到期后，当前下载完成便优先执行日志统计，再启动下一次下载；不会中断正在进行的下载。全局日志读取期间暂停源文件替换，目录轮询与评测继续。

下载先写 `.incoming/`，全部流式校验通过后才提升为源文件。下载的 `requestTimeoutMs` 约束等待响应或连续无数据进展的时间，收到响应头和每个数据块后重新计时，持续传输的大文件不会因总耗时超过这一值而中止。期间持有相关 run 的锁；开始替换前必须持久保存 `installing`，再进行多文件提升。刷新下载在替换前失败或被正常停止时，上一份完整输入仍为 `ready`；停止不记录成下载错误，网络故障保留原因及退避时间。已开始替换后的失败、进程崩溃留下的进行中状态，下次启动强制重新同步完整日期，再允许评测或发布日志。正式源文件位于 `data/sources/automations/<id>/<日期>/<模型>.jsonl`，不复制进 run。历史结果引用的原始本地源文件保留。

| 状态位置 | 内容 |
|---|---|
| `data/automations/<id>/state.json` | 唯一流水线账本：日期、run ID、观察/下载条数、下载/评测/交付状态、阶段汇总、重试时间、各轮 Mongo 写入数量与时间、全局日志 traceId/落盘时间/上传回执和错误；不保存回答或判词 |
| `data/runs/comparison/<run-id>/state.json` | Host 的权威逐任务状态、收据及恢复信息 |
| `data/runs/comparison/<run-id>/results/*.jsonl` | 各阶段正式结果，改写内嵌到源结果 |

下载状态为 `pending / downloading / installing / ready / retry`；评测状态为 `pending / evaluating / completed / waiting_inputs / retry / blocked`。每次状态变更原子写入账本，进程锁排除同一流水线的多实例；源目录另有锁，防止不同配置同时写同一数据源。

网络、下载失败持续指数退避，最大间隔 30 分钟。启动时先读取 Host 权威检查点核对流水线账本：取消、进程中断且没有真实失败的任务自动回到 `pending`，清除本轮错误、次数和退避时间；已保存的中断类阶段暂停在续跑时自动解除。Host 收到停止信号后的任务取消或清理异常不计入阶段熔断。始终复用原 run ID 和已接受收据，只执行未完成的归因、对比及其改写；聚类及其改写不进入自动化待重试池。

“等待新增输入”是正常状态，不作为红色执行错误；成功恢复后清除旧错误与退避时间。有已知剩余累计内容额度时，传输失败、响应流中断和超时会自动重试，并自动解除相应临时阶段暂停；Worker 终态提交账本不可确认也按此流程恢复，保留已确认计数和未确认原因，不补造或清零用量。每轮新增接受结果会重置连续失败预算；连续 3 轮没有新增结果才进入每 30 分钟一次的冷却重试，避免快速反复消耗额度。等待时间和次数跨重启保留，看板显示下次重试时间。启动时也会重新识别先前因最终计数缺失而 `blocked` 的日期，并自动安排续跑。

结构、证据、判决、文件等非临时校验熔断保持 `blocked`，普通未分类失败最多自动执行 3 次；错误显示具体阶段、分类、错误码或未完成数量，其他日期继续运行。已确认提交达到当前该阶段的累计上限（`1 + (execution.stageRepairAttempts[阶段] ?? execution.repairAttempts)`）时，该日期保持 `blocked`，不进入每 30 分钟冷却重试；重启、重复准备和材料修订不清零历史内容提交或文件错误计数。输入文件内容被远端修正时，自动解除旧暂停并在该任务原累计剩余额度内用新材料重新尝试；未变化的输入保持校验暂停。修复此类非临时校验问题后使用显式 `retry`。未达对应配对额度的缺配对输入或输入校验问题进入 `waiting_inputs`，等远端变化后重试；已达额度的缺配对不会阻止本轮完成，真实失败或未完成改写仍阻止完成。

主线来源核心未知或材料存在已知冲突时，保存待核结果，不产生正式胜负或上传该对局。其他可执行任务继续；只剩这些待核结果及其阻塞下游时，日期保持 blocked，不反复续跑已接受判词。可选独立核验通过显式命令执行，核验结果单独记录；它不自动重做归因，不影响主线正式结果的完成、改写或交付。

看板阶段数量分别统计完成、进行中、待执行、已中断、依赖阻塞和失败；`cancelled` 不计失败，`blocked` 表示前置任务未成功，不能解读为该任务已经运行并报错。真实的 `failed / timed_out` 才计入失败。

## 日志与进度

运行与评测日志沿用根目录 `log/runtime.log` 和 `log/evaluation.log`；统计上传记录另写 `log/comparison-statistics-log.jsonl`，不参与运行日志去重。`runtime.log` 记录发现、历史接管、下载开始/完成、输入更新、评测开始/结果、交付开始/完成/失败、重试、停机与错误，使用 `component=automations`、`automation_id`、`date`、`run_id` 关联。写入复用 Data 的跨进程锁、脱敏和完整行；错误逐条保留，不归并或截断正文、堆栈。重复正常状态在一分钟内合并，不为每次无变化轮询写日志。`evaluation.log` 继续由 Host 记录各阶段接受结果。

本地状态每 10 秒检查各 run 的文件身份与修改时间，仅重新读取发生变化的检查点；进度上报与看板共享进程内的阶段计数、用量、时段和远端进度投影，不保留检查点正文、草稿或评测结果。并发读取合并，文件替换、删除或解析错误使旧投影失效；读取期间发生替换时下轮重新核对。进程锁存活状态每次另行检查。评测恢复、Mongo 和统计发布仍读取权威文件，不使用监控投影作为结果来源。默认通过 `/evaluation-progress` 上报本流水线所有已登记日期的 Comparison 进度；每个 Fast/Expert 配对都有总数、完成、运行、排队、失败和预检跳过六项计数。未配对单列为 `skipped_cases`，中断与依赖阻塞计入排队，只有失败与超时计入失败；不将改写混进 Comparison 数量。远端看板的 Comparison 完成不代表本地已完成对应改写，以流水线状态为准。上报失败记录 `reportError` 并重试，不中断评测；错误包含 HTTP 状态和远端 JSON `error` 原因。远端只接受最近启动的上报者，旧上报者的 HTTP 409 会明确记录。关闭 `publishProgress` 可仅保留本地状态。

## 错误日志页面

看板右上角“错误日志”进入独立的 `/errors` 页面。默认近 24 小时，可切换近 7 天／全部时间及数据日期；按记录顺序从新到旧逐条呈现原始错误，每页 10 条，不预分类、不聚合、不改写错误内容。展开显示完整日志 JSON，保留来源已有的 run、任务、尝试、错误码、字段路径、期望值、实际值、原始原因和堆栈。每 5 秒刷新保留分页和展开状态；断连保留最后一页，页面不启动或重试任何任务。

来源仍是根目录 `log/runtime.log`，不另落错误文件，不改变冻结的统计日志。Host 每次失败尝试都会记录，包括随后恢复的失败；任务的结构化校验错误原样保留，Worker 或 Host 捕获的异常保留原始堆栈、cause 和附加属性。页面总数是已落日志条数，不是失败任务数；阶段暂停和通道失败也会形成独立记录。历史日志只能呈现原有信息，之前未记录或被合并的细节无法补回。

服务端只在首次读取和文件追加时增量建立轻量索引，按页从原日志读取完整详情；不每次刷新重扫整个日志，不将全部报错发到浏览器。日志未写完的最后一行等下一轮，不截断或修改日志。只呈现本流水线及其登记 run 的错误，响应继续脱敏。

## MongoDB 增量交付与每四小时日志

**上传日志格式已冻结**，唯一契约为 [`schemas/workflow/statistics-log.schema.json`](../schemas/workflow/statistics-log.schema.json)，保持已交付日志的字段、类型和层级不变。后续仅刷新统计值、标签内容和日期条目，最新一条仍包含累计总计及完整逐日统计。新增落盘和恢复续传均在上传前严格校验；缺字段、多字段、类型或层级变更直接拒绝，不转换、不删字段兜底。没有统计数据时仍保留固定字段，数组为空、缺失的指标值按契约为 `null`。除非用户明确要求修改这份外部契约，后续看板、统计和自动化改动均不得改变日志结构；测试随之约束生成及续传路径。

历史外部交付可以对目标集合做只读盘点，以 `mongo.verified` 保存核验时间、输入和输出数量。看板优先显示最新的成功回执或核验数量；核验显示“核验时间”，不生成上传事件或虚构历史上传时间，也不触发重新评测、重新上传。既没有回执也没有核验记录的日期才显示“未登记”。

MongoDB 在输入下载校验完成后开始同步，不等待整日评测或日志周期。随后在输入快照变化、可交付对比数量变化或需要补写改写文案时再次同步；每个日期两轮成功同步最少相隔一次目录轮询（默认 15 秒）。一个 Mongo 通道按日期串行处理，每批最多 100 条且目标 BSON 总量不超过 2 MiB；超过 2 MiB 的单条文档独立处理，仍受 MongoDB 的 16 MiB 单文档限制。完整文档游标每批读取 1 条，每次读取或写入单独使用 60 秒超时，避免整个游标共用短超时导致大输入重复失败。只有新增或内容变化的文档才写入。输入更新时间与可交付数量作为同步进度保存，没有变化时不反复扫描/上传。输入已成功同步且快照未变时，后续对比交付仅核对输入身份，不重复回读或上传完整 trace；缺失输入仍会补传。重启保留同步进度，中途失败通过业务键 upsert 续传；错误标明日期、身份读取/批次读取/写入及批次条数和字节量，便于定位。`mongo` 保存状态、重试时间和当前数量，`mongoHistory` 保留实际发生写入的历史批次；不复制输入或结果正文。目标集合为 `query_quality_new.agent_eval_bench_version_comparisons_new`。

日志按北京时间 **00、04、08、12、16、20 点**触发，**每轮只生成一条全看板累计快照**。包含配置范围内全部已登记日常批次，历史接管日期同样参与统计，但不重新评测。首轮在下一个四小时边界执行；停机跨过多个周期时，恢复后补一份当前快照，不伪造停机期间的统计。周期、traceId、落盘与上传回执保存在流水线顶层 `publication / publicationHistory`，Mongo 进度继续按日期保存。

每轮读取全部日期的原始输入及正式 `results/comparison.jsonl`，以批次、样本和模型为身份去重，不会把不同日期的同名题目合并。历史接管日期读取已有 run 登记的原始来源；当前远端已移走但正式结果仍引用的输入也从原来源补齐。普通自动化日期只纳入归因、对比及完整对比改写已接受的正式结果，读取 JSONL 时逐一检查最终偏好、双方整体总评和整场取舍的改写非空，逐格事实保持程序绑定的已接受归因；历史接管日期沿用已声明的阶段范围。随后重新计算胜率、准确率和耗时/Token 分位数，不拼加旧日志的百分位数。

所有日期使用同一种日志形态：顶层 `data` 是截至本轮的全局累计统计，`requestDates` 是完整的逐日统计。保留 `models / stats / tasks / progress / difficultyLevels / requestDates / winRateTrend`，全局 `scope` 为 `{ "matchup": "same-mode" }`，`source` 为 `/api/version-comparisons?matchup=same-mode`。`requestDates` 和趋势优先使用同一题任一模型提供的有效请求时间，按北京时间归日；全部模型都缺少有效请求时间时使用所属日期批次，避免题目计入总量却不出现在任何一天。每个 `requestDates` 元素包含 `date / count / caseCount / totalCaseCount / models / stats / tasks / progress / difficultyLevels`；其中 `count` 等于该日 `totalCaseCount`，`caseCount` 是至少完成一场对比的题数。逐日元素不再嵌套 `requestDates` 或重复趋势。

所有模型统计和 `winRateTrend` 均按 `wins / both_good / both_bad / evaluated` 顺序输出同级字段：`both_good` 为双方都好、`both_bad` 为双方都差的对战数，均为必填非负整数，无此结果时为 `0`。累计、每日、场景、难度及难度下场景的 `stats` 共用这一口径，直接读取正式对战的 `verdicts.*.result`，不从空胜者或准确率推断。双方模型各记一次其参与的该类对战，A/B 计数相同；同组满足 `A.wins + B.wins + both_good + both_bad = evaluated`，不能再把 A/B 的 `both_*` 相加作为对战总数。胜率仍为 `wins / evaluated * 100`，其他字段、层级及分母不变；这两个字段纳入冻结契约。

每轮都保留全部历史日期、刷新已有日期的最新数字并纳入新增日期，消费者只需读取最新一条即可获得全部统计；同一天的后续完成结果会回填到那一天，总计同步更新，不重复累加。全局和每天的耗时、Token 分位数均从原始数值分别计算，不能平均每天的分位数。各周期的日志不能相加。

分类与难度读取输入 `meta.task / meta.difficulty`，并从目标 Mongo 集合中读取这些字段的后补标签。通过批次和原始 `case_id` 对齐，同一题的模型共享分类；不根据模型 ID 猜测映射、不改动原始输入或 Mongo 标签。同题难度取 Mongo 中 `createdAt` 最新入库记录的值，覆盖本地输入与较早记录的难度；时间相同时取 `_id` 排序最后的记录，确保读取结果稳定。最新记录的难度为空、未分层或不在已定义等级中时归入“未分层”，不回退到旧标签；没有 Mongo 记录时沿用本地输入标签。此口径按入库时间选择，不代表标签最后修改时间。难度差异不阻断统计，保留总量、胜负、双方都好／都差和已知分类统计。分类冲突或标签来源读取失败仍拒绝本轮快照，保留上一份完整快照，不静默生成全未分类的日志。来源确实没有标签的题仍显示“未分类／未分层”，不推测分类。统计不依赖 Mongo 交付是否完成，但需要成功读取当前标签。

先将完整记录追加到 `log/comparison-statistics-log.jsonl`，再逐条 POST 到 `https://aime.myhexin.com/agent-eval/api/logs`，不设置 `filePath`。只有 HTTP 201、`written: true` 且有 `requestId` 才确认上传成功。本地同一 traceId 不重复追加，不重传历史评测结果。Mongo 刷新原始输入时，缺失的分类、难度字段保留库中后补标注；原始输入显式提供的标签更新仍会同步。

需要立即补一条全局日志时，停止流水线后执行 `npm run automations -- publish-log`。此命令只统计、落盘和上传日志，不调用模型；上一条尚未成功的日志复用原 traceId 和已落盘内容继续交付，成功后清除本轮错误，只有已完成记录进入交付历史；下一轮仍按原来的四小时整点执行。

Mongo 输入用 `kind=input`，评测结果用 `kind=comparison`；所有新写入使用 `a_fast / b_fast / a_expert / b_expert`。输入保留 `versions`、`task`、`meta` 和原始消息。comparison 保留归因评测及内嵌改写，含 `result.comparison`、`versionA/B`、`evaluatedAt`，专题 `task` 与对应输入一致，不另写 attribution 文档。`versionA/B` 按稳定版本 ID 排序；Workflow 根据源 Comparison 检查点保存的 `inputIds → inputs[].version`，将改写候选槽位从盲测 A/B 转为这两列的位置。整体总评和已接受的逐格点评使用同一映射；整场偏好与取舍保持原文，不按正文称谓或 JSON 字段顺序猜测归属。映射缺失、不匹配或槽位重复时拒绝交付。本地收据、JSONL、判决与证据不因此改变，每次上传或续传均从本地原始槽位重新投影。沿用已有原始 case 对应的数据库 ID；新 case 用持久化 UUID。业务键 upsert，已存在且内容相同的记录不重写，部分批次失败可安全续传；不删除、不迁移其他日期或旧模型记录。当前目标集合的旧 comparison 校验器不接受已在使用的顶层 `task`，沿用既有上传方式，仅对 comparison 写入使用 `bypassDocumentValidation`；输入仍受校验器约束，集合配置不修改。

Mongo 与统计日志共用输入隔离规则：先完整扫描当前日期的输入，按日期、原始 `case_id` 和模型识别重复；同一标识的全部记录均排除，即使内容相同也不任选一条。仅引用冲突模型输入的对局暂缓交付，同题其他有效模型对和其他题目继续上传、统计。隔离只影响本轮交付视图，不删除或改写源文件、已接受任务、收据及正式结果，也不触发重新评测；旧输入回补不能绕过隔离。冲突标识写入现有 `log/runtime.log` 的 `publication_inputs_quarantined` 事件，统计 JSON 结构不变。上游修正输入并完成刷新后，下一轮重新扫描，原有已接受结果可直接恢复交付。扫描与后续读取校验同一文件修订，文件被替换或修改时明确重试，避免用旧隔离清单处理新内容。

Comparison、本题归因及它们全部已计划改写都有正式接受收据，即将 `results/comparison.jsonl` 的对应完整行增量上传到 Mongo，并纳入统计；不等待整日结束或聚类。聚类及聚类改写后置，不计入自动化完成条件和交付等待。不会上传未改写的归因或对比结果。评测仍在进行时可以上传其他已经满足条件的题目。输入缺配对计入输入总量，不算已完成对战；胜率、准确率及耗时/Token 分位数只基于已交付对战，沿用示例日志的字段结构。`logtime` 为实际落盘的北京时间。

`publication.status` 为 `pending / running / completed / retry / uncertain`，保存日志下次执行时间、次数、统计数量和错误。本地落盘失败指数退避重试，Mongo 故障不会阻止日志统计、落盘和上传；线上日志需要核实回执时，Mongo 仍继续增量交付。

线上日志是追加接口，没有去重或删除能力。POST 前先持久化 `sending`；超时、响应异常或进程退出后无法确认是否已写入时进入 `uncertain`，停止该条全局日志的自动重发，评测与 Mongo 交付继续。本地同一 traceId 不重复追加；已成功的回执不重复 POST。停掉流水线，在日志平台按该条 traceId 核实后选择：

```bash
# 已确认线上写入，填写核实到的请求编号
npm run automations -- resolve-log --outcome written --request-id req-123
# 已确认线上未写入，允许重发原有本地记录
npm run automations -- resolve-log --outcome retry
```

随后执行 `run` 继续；此命令只处理日志回执，不重做模型评测。

## 模块

调度与状态机在 [`packages/automations`](../packages/automations/src/index.ts)，只依赖 Contracts。HTTP 取数、Mongo 和日志上传属于 Runtime；源文件提升与统计日志 IO 属于 Data；正式交付筛选与统计属于 [Comparison Workflow](../packages/workflows/src/comparison/publication.ts)；共享只读监控投影位于 [`automation-monitor.ts`](../apps/host/src/automation-monitor.ts)；配置、历史接管及组装位于 [`apps/host`](../apps/host/src/automation-command.ts)。评测规则和 Worker 执行仍使用原有实现。
