# 临时夜间三路评测

`scripts/night-eval.mjs` 在同一个进程内分配问财、AIME 流失用户、AIME 日常的模型请求额度。先在 worktree 开发验证，合并就绪后才由操作者在服务器启动；不会部署、注册自启或修改外部清洗服务。

## 启动与交付

使用已完成 bootstrap/build 的服务器 checkout。默认配置为 `configs/night-evaluation.json`，读取服务器 `runtime/config/config.ini` 的两个渠道，并通过 `automations-host.json` 选择当前评测模型与 low thinking。INI 路径和 `hostConfigs` 可指向 checkout 外的现行配置；路径相对该 JSON 解析。启动前用 `check` 核对实际输入、渠道和清洗状态。

```bash
node scripts/night-eval.mjs check
node scripts/night-eval.mjs run
node scripts/night-eval.mjs status
node scripts/night-eval.mjs close-input
```

需要 SSH 断开后保持运行时，先进入 tmux。所有命令支持 `--config /absolute/path/night-evaluation.json`。`check` 只读，不收包、不瘦身、不调用模型。`run` 首次锁定两路日常输入，以及操作者已经放入流失瘦身目录的存量文件及记录坐标，后续同一状态目录只恢复已锁定范围。启动后日常源文件须保持稳定，源被覆盖或追加会明确失败；不会偷偷改变今晚范围。

| 来源 | 工作流 | 正式输出 |
|---|---|---|
| 问财 | 当前 Comparison，含配置启用的阶段 | `/mnt/fin_bench/eval_data/0_wencai/eval_output/0_daily_eval/<业务日期>/` |
| AIME 流失用户 | Attribution | `/mnt/fin_bench/eval_data/1_aime/eval_output/3_lost_user_eval/lost-<UUID>/` |
| AIME 日常 | Attribution | `/mnt/fin_bench/eval_data/1_aime/eval_output/0_daily_eval/<业务日期>/` |

正式结果遵循各 workflow 的现行契约，AIME 在 `results/attribution.jsonl` 增量落盘。既有 `.archive` 不读取、不移动、不计入覆盖。本管线交付上述本地结果，独立于工作台的持续取数与 MongoDB 交付服务；运行期间不要再用其他评测进程占用同一日常 run 或这份模型请求额度。`3_lost_user_eval` 当前不会自动出现在只枚举日常、专项和测试目录的助手检索入口。

## 调度

当前配置 `activeSources: ["lost"]` 暂停问财和 AIME 日常派发，只运行 AIME 流失用户，使用全部可用模型请求额度。总上限仍为 400、每网关 200；暂停来源的输入、进度、成功收据与累计预算保留，重启不会自动恢复。重新启用必须显式修改 `activeSources`。

当前运行额度 `requestsPerChannel: 128`，每网关最多 128、合计最多 256 个实际模型请求，仍受原每网关 200、总计 400 的安全上限约束。降低运行额度只限制新许可，在途请求自然释放；任务、成功收据与累计预算不重置。

协调器支持 `SIGUSR2` 重新读取配置中的来源选择：配置保存后，对活动协调器执行 `kill -USR2 <PID>`。只更新 `activeSources`，不替换运行实例、输入范围或模型闸门；移除来源停止新任务派发，在途自然收尾后保留原 run 待续跑，其他来源继续派发、执行和落盘。收尾期间原来源的在途模型请求仍计入同一网关硬上限，释放的许可立即由其他等待请求使用。此操作不重启整个协调器，也不要求所有来源排空。

流失用户内部按已登记交付的业务日期升序选择可运行批次：先处理 9 月 17、18、19 日，再继续 10 月数据；同日保留入队顺序。更早日期就绪时，较晚日期批次停止派发新任务，在途收尾后保存为待续跑；仍使用原 run、成功结果与累计预算。失败批次保持失败，不重新入队，也不阻挡后续日期。此优先级不改变两路来源权重、并发限制或输入输出范围。

1. 仅启用的来源运行，通常按各自批次顺序处理。某批无待派发或准备中任务、仅余最多两个在途任务时，可预热同来源下一批；每路最多两批，全管线最多一个额外批次，仍共用现有模型请求额度，不打断尾部任务。问财仍只选择业务日期 **2026-10-23 至 2026-10-27（含首尾）** 的启动快照，完成后不接收新增问财数据；续跑保留既有输入坐标与 run。
2. 两个网关分别硬限 **200 个实际模型请求**，整条管线最多 400。多个来源启用时沿用问财 7、流失 2、AIME 日常 1 的相对权重；当前仅流失启用，不为暂停来源预留额度；无待发请求的来源不预留空闲额度，其他来源可立即借用。工具调用和材料准备不占请求许可。
3. 流失存量首次登记后即可评测，新增瘦身文件每两小时登记，不打断另两路。额度只约束该管线，外部清洗等其他进程在相同网关上的请求独立计算。
4. `runtime/state/night-evaluation/model-requests.json` 每十秒记录三路在两个网关的实际获批、活跃与排队请求数，`status` 同时展示。记录仅用于运行观察，不是正式结果或统计上传日志。

每日批次规划只读取该日已登记坐标引用的源文件，不重复读取其他日期的正文；恢复仍使用原 run 的已接受结果与累计预算。

Comparison 优先派发已经就绪的比较、归因汇总与组件任务，最后再展开新的标准分析，避免短标准任务持续挤占长组件任务所需的并发，优先交付完整回答的结果。

模型额度也在每路内部按比较、会话汇总、trace 汇总、组件、标准分析的顺序领取，同级保持先来先服务；跨来源仍先按启用来源的相对权重选路，再在该路选请求，避免汇总被已排队的组件请求长期挡住。

夜间入口将本机地址与配置中的模型网关主机加入代理绕过列表，避免服务器的外网代理接管 Host/Worker 本机通信或集群网关请求。

请求额度领取失败仍阻止模型调用，但网络故障保留自动重试资格；额度释放使用同一请求坐标进行短暂重试，不因偶发连接重置丢弃已经完成的模型轮次。当前 Host 配置允许三次网络重试，内容修正预算保持独立累计。

等待模型额度的 HTTP 连接每十五秒发送 JSON 空白保活，只有获批后才返回许可对象，避免低权重来源长时间排队触发 HTTP 空闲超时、误消耗网络重试预算。已有累计预算与失败状态保持不变。

托管 Worker 启动后的健康检查遇到网络故障时，只向待派发任务累计网络失败与退避，不中止同批其他已运行任务；累计预算耗尽后该任务记失败，继续其他可执行任务。

夜间托管 Worker 每个进程提供八个独立会话槽位，复用模块与连接池以减少进程内存和启动开销；模型请求额度仍由三路共享的加权请求闸门控制。进程退出后的故障槽位独立替换，成功收据不重评。

续跑从进度事件流尾部读取检查点之后的增量；首次追加也只读取末条序号，避免重复解析数 GB 的已保存历史。增量仍校验连续序号和本地热状态的一致性，不删除历史事件。

恢复归因任务身份时只为当前回答的历史任务建立索引，避免每条回答重复序列化全批历史任务；任务 ID、收据与累计预算保持不变。

正式结果投影与统一评测日志补写分别串行执行，慢日志不会阻止新的已接受结果落盘；收尾仍等待日志写入。

普通任务收据只追加本次结果与状态，不重复附带整批输入目录和任务顺序；输入目录由初始状态与检查点保留，新增后续任务时才追加任务顺序，避免大批次的重复元数据挤占正式结果落盘。

同一 run、同一输入 trace 的组件共享已组装的只读公共材料，组件场景、证据读取证明和任务收据独立生成；输入对象或标准分析变化时重新组装，run 输入释放后材料索引可回收。此索引不复用评测结果或跨 run 数据。

统一日志将已排队记录批量追加并同步，复用一次跨进程写锁；每条调用仍在对应批次持久化后才返回，保留去重与全部错误记录。

当前 Host 配置关闭阶段熔断。每个任务的网络失败最多重试三次，失败计数随任务持久化，重启和切换网关不重置；首次调用加三次重试均失败后保留失败终态，继续可执行的对战。成功任务不重评，原内容修正预算仍累计。失败批次不会自动重新入队，重启也不恢复失败批次；只恢复中断的在途批次，并跳过其中已经失败或阻塞的任务。失败如实统计，不算成功，也不阻塞其他来源或后续批次。

日常启动快照中，单条格式错误或缺少有效问题的记录进入状态和统一日志的 `excludedInputs`，不阻挡其余有效记录。Comparison 同时排除该业务日期、case 的其余候选，避免生成不完整对局；Attribution 仅排除无效记录。`status` 展示排除坐标与原因。重复身份、文件不可读和输入变动仍明确报错，原始输入不改写，不把排除记录算作评测成功。

## 流失数据链路

启动前由操作者补齐 `6_lost_user_eval_clean_slim/{aime_fast,aime_expert}/` 的存量 JSONL；每个文件只包含一个业务日期。首次启动逐行检查瘦身格式、业务身份、重复与文件稳定性，将存量直接登记到评测队列和持久化去重索引，不重复瘦身或复制正文。隐藏目录与 `.archive` 不参与。存量入队后不得覆盖或追加原文件；后续新增压缩包继续走下面的自动链路，生成独立增量文件。清洗输出再次包含存量时，只核对正文一致，不重复交付或评测。已有状态的重启直接恢复索引，不重新导入存量。

以下路径相对 `/mnt/fin_bench/eval_data/1_aime`：

| 环节 | 目录 |
|---|---|
| 收包 | `1_7z_data/lost_user` |
| 原压缩包归档 | `1_7z_data/lost_user/3_processed_archives/<YYYYMMDD>/` |
| 解包规范输入 | `5_lost_user_eval_input` |
| 外部清洗输出 | `6_lost_user_eval_clean` |
| 瘦身交付 | `6_lost_user_eval_clean_slim/<模型>/<日期>-<UUID>.jsonl` |

每 30 秒逐包检查稳定性，正在写入或发生变化的包等待；坏包保留并报错，其他包与已有清洗输出继续处理。沿用已存在的 `.extract-lost-user.json` 进行增量提取，断点缺失、损坏或同名冲突明确报错，禁止自动全量重建。与既有 `watch-lost-user.mjs` 共用规范输入目录的实例锁，避免两个 watcher 同时追加。手工 extractor 也不应与管线并发运行。

Python 数据适配器的子进程创建与收发由专用 Worker 线程执行，避免大内存 Host 在 Linux `spawn` 时同步阻塞模型额度、本机 HTTP 与结果落盘。适配器操作和错误仍由原准备循环处理，不重试已提交的数据操作，不改变模型请求闸门、评测任务或预算。

按清洗 `status.json` 已提交的 `output_records` 读取输出 JSONL 的完整记录前缀，先瘦身再交付评测。`processing`、`completed_with_backlog` 和持有整轮清洗锁都不阻挡已提交记录；未完成标注或翻译的记录继续等待清洗服务补齐，后续以新业务身份增量交付。清洗器先持久化追加记录，再原子更新提交计数；未计入该计数的尾部不会进入评测。只有状态 `completed`、输入游标与解包回执一致且 backlog 清零，才把该文件标记为全部收尾。管线不启动、停止或重启外部服务；剩余等待原因和错误通过 `status`、统一日志查看。

瘦身复用现有消息池转换并逐行反向还原校验。每轮仅捕获清洗 **输出** `output_records` 对应的前缀到临时文件，允许清洗正常过滤输入。发布前逐字节核对该前缀，文件替换、截断或前缀改写会延后并报出原因；正常追加不阻挡发布。临时原文随本次操作清理，评测只引用已经发布的不可变瘦身文件。每轮交付一次后返回，避免持续追加让单个文件独占准备循环。

每个成功交付文件保持不变，后续同日期仅发布新业务身份。索引只保存业务标识、文件坐标和元信息；既有身份若正文改变、被删除或同批重复则报错，不能静默沿用旧结果。崩溃发生在文件发布和回执保存之间时，通过持久化发布意图恢复，避免重复加入评测队列。输入正文只在数据源目录，不复制到每个 run。

## 收尾与恢复

`close-input` 保存截止时收包目录已有的包名，之后的新包不纳入本次任务；截止时仍在上传的包继续等待稳定，已接收数据继续等待清洗和评测。收尾阶段就绪数据立即登记，不再等待两小时间隔。清洗等待、归档错误和失败任务没有解决前不会报告全部完成。没有执行 `close-input` 时持续监听，不把暂时空队列当最终完成。

Ctrl+C/SIGTERM 停止三路继续调度，等待已派发任务和当前数据操作收尾。同命令重启沿用 `runtime/state/night-evaluation/state.json`，不会重新扫描归档的旧评测结果。状态损坏报错，不自动丢弃重建。截止范围的任务都结算后，有失败时记录 `finished_with_failures`，不报告全部成功。控制与状态只在既定 runtime 目录；日志由 `@eval/data` 写入 `runtime/log/runtime.log`、`evaluation.log`，无新增运行日志文件。

本地验证使用临时合成数据与模拟 Worker，不写服务器真实产物。需要真实小样本验证时，另走既有 CLI 的 `--test-eval` 和对应来源 `test_eval/`，不要用本管线的正式配置试跑。
