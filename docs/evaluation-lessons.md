## 2. 最核心的教训：用有效交付衡量优化

用户需要的是能读懂、能核验的 `comparison.jsonl`。归因成功数、Worker 数量、模型请求数都是过程指标。后续应以“每分钟新增多少场已落盘、满足本轮改写要求的对比”作为主要吞吐指标，并同时显示返工率和失败原因。

本次逐项改写曾把两个大日期各提高到 160 并发，同时运行。这个数字说明该次配置曾被使用，不能据此认定它是稳定最优并发，也不能直接外推到更长的归因任务。小样本时请求成功、类型检查通过，都不足以证明整批任务已经适合放量。

对于 6,256 场、120 分钟的目标，平均至少要形成约 **52 场完整交付/分钟**，还必须给启动、尾部失败和最终核验留时间。应先测端到端净产出，再决定容量；不能只拿模型平均响应时间估算完成时间。

## 3. 调度与恢复踩过的坑

| 坑 | 为什么浪费时间 | 本次已解决 | 仍需完善 |
| --- | --- | --- | --- |
| 等整批归因结束才推进下游 | 已有足够依赖的对比和改写也排队等待 | 按单任务依赖推进；就绪阶段共享空闲槽位，避免上游积压饿死下游 | 用完整对比产出监控阶段饥饿，而不只看总运行数 |
| Worker 繁忙或派发前不可用，被当作题目失败 | 容量故障扩散为大量任务失败，浪费重试预算 | 不消耗题目 attempt；暂时隔离 Worker，恢复后重新纳入；长期无容量则保留待执行任务退出 | 汇总容量故障，避免人工从几千条错误里判断同一故障 |
| 上游处于重试间隔，下游提前永久 blocked | 暂时失败被误判为最终失败 | 结合运行中的执行链判断依赖状态，上游仍在重试时下游等待 | 增加各类重试中断组合的回归覆盖 |
| 断流与内容错误混在一起处理 | 网络波动重复生成内容，规则错误则不断原样重试 | 对中断流做有界传输重试；内容修复保留独立预算 | 增加批次级同类错误暂停机制，不能只靠单任务预算 |
| 已连续失败的草稿进入下一次尝试 | 新尝试继续沿用错误数字和错误结论 | 停止草稿不再进入新 attempt 的提示和草稿文件；保留可行动的错误信息 | 记录“重复错误被切断”的比例，验证恢复实际有效 |

这些是调度和恢复问题，不能靠把并发从 48 改成 128 来解决。实现入口：[阶段调度](../packages/host/src/scheduling.ts)、[Host 运行](../packages/host/src/runner.ts)、[Worker 恢复](../packages/runtime/src/server.ts)。

“同步跑对比”应解释为各样本独立流水执行。某个对比仍须等待它自己的有效归因依赖，不能为了赶进度绕过依赖或使用失败草稿。

## 4. 校验器本身也会错，不能把所有拒绝都归咎于模型

本次遇到的数值边界包括：科学计数法精度、区间连接符与负号、日期后接负数、“跌”表达的方向、中文数量、减法右操作数，以及数值紧贴下一段年份。

典型例子是 `8.362025 年上半年`：应识别数值 `8.36` 与后续年份 `2025`，不能把整串当作 `8.362025`。类似地，`|20000−19684|` 中的 `19684` 是减法操作数，不能机械解析为带负号的数值。

本次已补充解析与回归用例，并让数值错误反馈携带实际解析的引用原文。处理方法应固定为：**抽取最小原文 → 重现解析错误 → 写回归用例 → 修解析或规则 → 只恢复受影响的未完成任务**。不能为了通过而放宽正确性标准，也不能用模型重试补偿确定性的解析错误。[数值回归](../packages/agents/src/attribution/numeric.test.ts)

旧成功结果可能采用不同的 `evaluatorVersion`。当前校验发现历史异常时，应记录异常和适用范围；没有明确重评指令，不批量重置旧结果。更改提示、材料组装或校验后，也不能把旧收据统一改标为新评测器。

## 5. 公平比较必须保留各自的系统约束

用户提醒的例子非常关键：一方要求风险提示前置，另一方要求不要前置，不能拿某一方的系统提示当作双方共同标准。

本次已让各回答的 system/developer 约束完整进入材料，并提醒对比按本候选约束检查。这里还要区分三件事：

- 是否遵守自己的约束。
- 是否交付用户需要的结果。
- 在允许的范围内，哪一方的交付更有用。

合法的权限限制不等于模型能力错误；但仅说明权限不足，也不自动等于交付了用户所要的结果。改写阶段更不能重新解释约束、推翻旧归因或代替裁判重新判胜负。[当前质量规则](quality.md)

## 6. 改写返工最多：材料边界与语义验收建立得太晚

### 偏好不能丢在泛泛总结里

“双方都完成了核心要求，未见共同遗漏”无法解释为什么最终判某一方更好。偏好改写必须锁定既定结论，再从本场事实解释取舍。局部问题不能悄悄推翻整体胜负，整体赢家也不能抹掉另一方的局部优势。

本次已把偏好作为固定约束，校验胜者前缀和并列判决。偏好理由与逐项点评分别选槽位，刷新逐项点评时保留已有偏好。

### 对照信息混进正文，导致标签和主体串位

最初将“本格原文、已定优势、另一方表现”拼在同一段 `text` 中，模型会把辅助信息也当成待改写正文。实际出现过：

> A组Fast：AA组Fast主要列财务指标和概括性风险标签……

也出现过以“没有已证实的单方优势：”开头的机械标签。JSON 格式正确、槽位齐全，仍然不适合交付。

本次先把本格 `text` 与只读 `context` 分开，再增加 `forbiddenPrefixes` 校验，拦截把其他模型标签或辅助标签贴到正文开头。仅修改提示后仍有残留，说明必须把可明确判断的错误交给程序拦截，不能只重复强调“不要”。[槽位组装](../packages/workflows/src/comparison/commentary.ts) · [Rewrite 校验](../packages/agents/src/rewrite/validate.ts)

### 犀利不能扩大事实

实际出现过把“未逐公司展开……证据”写成“未逐公司核查……证据”。前者说明交付里没展示，后者断言没有做相关工作，已经改变含义。

当前提示明确保留不确定性，并禁止这种扩大。文风验收应关注“关键得失是否具体、主语是否准确、限定是否保留”，不能只关注是否更短、更有力度。关键词扫描用于找疑点，最终仍须结合原文判断；例如原文已经写明“月份未确认”，改写成“头寸未核实”不应仅因字面变化被判错。

### 执行上我应该更早做的事

这轮最初以少量成功样本和测试通过作为放量依据，没有先检查足够多的整场输出与全部槽位。放量之后才发现共性的模板复制问题，产生了大批返工；这是我的执行问题，不应归因于用户追加了改写要求。

正确顺序应是：**代表性样本的语义验收 → 已知错误的全量自动检查 → 扩大流量 → 持续抽查**。启动后发现共性问题，要暂停受影响的新派发并修代码；其他健康阶段继续。不要反复重启整条任务链。

## 7. 本机的内存、构建与持久化同样在关键路径上

本次修复了检查点深拷贝大判词和整日原始输入常驻内存的问题：检查点复制可变进度及收据外壳，已接受正文保持不可变；原始输入按记录定位、按需读取。发生过正式结果和结束状态已写完、附加报告阶段才内存退出的情况，因此进程退出码、正式结果完成和报告完成必须分别判断，不能为补报告重跑评测。

仍有两个明确的工程风险：

1. [结果写入器](../packages/data/src/repository.ts)回填改写时会更新对应 JSONL 整体；[状态保存](../packages/host/src/store.ts)虽已合并部分并发保存请求，仍可能承担较大的序列化与写盘成本。先测写入耗时、队列积压和事件循环延迟，再决定是否批量合并回填；不能未经测量就断言这是当前最大瓶颈。
2. 常规[构建脚本](../scripts/build-app.mjs)会先删除部分 `dist`。活跃 Worker 仍可能需要其中的工具入口，不能在共享运行目录上直接清理重建。本次用了临时原位构建脚本；长期应提供正式的独立构建输出或隔离构建流程，验证后仅供新 Worker 使用，让旧 Worker 完成在途任务。原位覆盖仍不是完整的运行隔离方案。

不建议立即引入数据库、跨 run 结果缓存或一套通用调度平台。先测量并修复当前写入与生命周期边界，保留已经验证的恢复顺序和原子落盘保证。

## 8. 按日期增量必须明确区分三种操作

| 操作 | 可以变化的范围 | 必须保护 |
| --- | --- | --- |
| 原日期增加输入 | 原选择范围内新发现且可配对的业务任务 | 已接受的归因、对比、改写 |
| 只补失败 | 明确选出的失败/未完成任务及其必要下游 | 既有成功收据、尝试次数和正式字段 |
| 只改写文案 | 明确选中的结果与槽位 | 判决、归因、证据、未选中的文案 |

0926、0927 应各自创建日期 run，不能为了新日期重跑 0922—0925。原日期追加数据也不能使旧成功样本重新进入模型请求。评测范围用业务标识、任务 UUID 和既有索引核对，不引入源码哈希或跨 run 结果缓存。

这次运行中冻结补跑范围和保护旧结果主要依靠 `.artifacts` 下的一次性脚本。复盘后已将任务/结果/槽位选择、默认预览、只补缺失、显式刷新和固定续跑范围纳入正式入口；不再需要为这三种操作手改 state。使用方式见[失败补跑](usage.md#只补失败与同类故障熔断)与[文案修复](usage.md#重新改写对比文案)。

## 9. 下一步按这个优先级改

以下按复盘后的落地范围更新。已实现项仍需真实模型小批验收；故障注入和结构回归不能证明模型语义正确。

| 优先级 | 改进 | 主要位置 | 验收标准 |
| --- | --- | --- | --- |
| P0 | 已实现：task ID、结果 ID、槽位选择、预览与固定范围 | Host CLI、Comparison Workflow | 单格回填保护其余字段与成功 attempt；追加输入不混入；纯改写不依赖原始输入 |
| P0 | 已实现基础：8类固定对照样例、分层试跑、全格审阅入口 | agents/rewrite、Workflow、质量指南 | 含真实返工与明确标注的受控变体；结构反例自动回归，语义反例人工核对，不自动批准放量 |
| P0 | 已实现：同阶段错误签名熔断与显式恢复 | Host、进度输出 | 不同任务触发阈值即停止新派发；健康阶段继续；暂停跨重启；定向恢复不越过原范围 |
| P1 | 部分实现：分阶段产出、目标并发与实际占槽区分 | Host、进度统计 | 仍需端到端时间序列、写盘积压与实测反馈，暂不自动调整并发 |
| P1 | 监测并优化 JSONL 回填与检查点写入 | Data、Host Store | 用真实大文件测 P95 写入耗时、峰值内存、恢复结果；优化后故障恢复不丢已接受收据，不新增第二份正文存储 |
| P1 | 已实现：在 validate 声明日期与改写要求 | Comparison Workflow、CLI | 检查日期、业务键、完整性、收据与原字段、指定槽位及全部指定文案的当前机械约束；证据异常和语义待审分开呈现 |
| P1 | 将运行与构建隔离、报告独立执行变成正式能力 | scripts、Host、Runtime | 活跃任务期间构建不破坏在途 Worker；报告失败可独立重做，不触发评测 |
| P2 | 衡量裁判质量和改写语义保真 | 真实回归集、人工复核 | 记录位置交换稳定性、偏好一致性、事实扩大率和人工分歧；结构通过率不再代替内容质量 |

当前默认熔断为每阶段最近50个不同任务中，相同类别、错误码及归一化字段路径达到5次；同一任务重复尝试只计一次，暂停整个受影响阶段的新派发。窗口与阈值可配置，仍需实测校准；相同签名不意味着一定同根因。容量、网络、结构、证据和语义错误应分别判断，不能使用一个总重试按钮处理。

## 10. 下次执行的最短流程

1. **明确本轮交付范围。**列出日期、配对场数、未配对/无效输入、必需改写槽位；区分新增数据、补失败、改写三个意图。预算不足时优先保证约定交付，聚类等独立工作单独安排。
2. **做代表性小批验证。**建议先选 30—50 场，覆盖上一节的边界类型；检查整场各格，而不是只看前两行或成功数。出现共性问题先修代码。
3. **逐步放量。**以当前服务实测为准递增并发，观察实际在途请求、各阶段有效产出、错误类别、P95 延迟和写盘积压；不把本次 160/日期当作下次默认值。
4. **流水推进，局部处置失败。**归因就绪即进入本场对比，对比就绪即进入指定改写；少数失败进入明确清单，同类系统故障暂停受影响部分，健康工作继续。
5. **增量写回并持续验收。**原判词不覆盖；样本改写接受后立即检查槽位、主语、偏好和不确定性。出现质量回炉时，只修异常槽位，避免整场全部文案再次生成。
6. **核验交付，再释放资源。**必须看到四个 JSONL 的完整性、保护核验和明确的异常清单；Host 自然完成后关闭专属 Worker。最终报告同时交代完成数、返工数、失败数和仍未验证的范围。

后续执行以已落地的试跑、定向修复和熔断为基础，继续校准真实模型语义验收、有效交付吞吐和写盘成本。构建隔离与自动调并发尚未完成，不据此承诺下一轮的完成时限。
