# 评测质量

[返回首页](../README.md) · 机器可校验的结构和证据规则见[数据契约](contract.md)。

## 评语标准

归因与对比的初始材料完整保留每条回答各自的 system/developer 消息，不受历史材料长度预算裁剪。裁判据此按各自指令层级检查任务约束；候选特有要求不作为双方共同标准，相反但各自合规的要求不能单独决定胜负。原始提示属于约束证据，不改变裁判的流程与提交规则。已接受结果保留；新任务使用当前 `evaluatorVersion`。旧归因与共同标准、标准答案或当前材料不一致时独立复核；Comparison 发现归因冲突时请求复核，不自行改判或改写旧行。

模型可见的阶段规则、工具描述和材料边界只在[提示词模块](../packages/prompts/README.md)维护；公共片段只包含材料分隔、预算和恢复说明；阶段提示词按实际可见材料及可用工具写核验、提交规则。Criteria 从程序提供的完整原文段落目录选择来源，程序固定要求文本、候选范围和验收规则；不让模型重写数值、单位或容差。每个候选的要求必须包含题目和已有标准答案，具体换算由归因阶段核算。归因逐项核验并给出条件性对错判定、总点评和有证据的优点及确定/疑似问题；不读写问题库，不携带对比判决。总点评概括主要正反事实，不逐条复制 findings；没有可核验的优点或缺陷时不凑数。Comparison 读取归因与 trace 的去身份视图，默认归因结论正确、只做确认与核验。纯结构修复不重复核验已确认事实；改变事实判断时重新核验相关材料。

`assessments[].summary` 一句说明各候选的主要表现；`decision_basis.comparisons` 按同一方面逐行对照全部候选，关联既有 findings 并标记重要性及本项优势。`tradeoff` 只写裁决和决定胜负或都差时相对取舍的一至两项具体事实，通常一至两句，上限100字，不凑字数或固定句型；比较格和候选 summary 上限160字，这些原评测字段保持原文，逐项点评的改写另存于 `rewritten`。细节与不改变排名的局部瑕疵留在对应比较行；真正影响取舍的反向事实必须保留，说明新增了哪项结果及其代价，不用“核验价值”“额外等待未换来同等价值”等抽象套话代替事实。`verdicts[].reason` 原文由核心要求判定和排名派生；其改写槽位必须以既定偏好开头，并根据同场原裁决和比较项补充具体理由。

结论先回答谁更好、为何都好或为何都差，再解释足以改变结论的事实。按[判决契约](contract.md#归因与判决)区分标准答案一致性与关键交付可用性：局部偏差不自动使主要结果不可用，归因判错事实仍保留。可用性须看整份最终回答，不能只看主表或复制归因的重要性等级；后文已明确交付的结果不能说成没有交付，如实说明权限不足但未给所求结果也不算完成查询。都差仅用于有已证实问题且双方关键交付都不可用，此时仍同层，但对比裁判须在 `tradeoff` 根据逐项事实写清哪方相对更好及原因，权衡错误影响、剩余有用内容与修正代价；无足够依据区分时明确说明，不硬选。相对优势不代表达标或正式胜出；都好仅用于双方可用，且检查内容、耗时和 token 后没有实质差距。双方均可用时，仅一方存在中高重要性优势则分胜负，有反向优势时按题目需求权衡，不用“各有优劣”跳过比较；也不为压低并列比例硬造差异。判赢家时说明用户采用该回答会在哪项结果上获益。

每条评价都应串起「具体观察 → 可核对证据 → 判断依据 → 对用户的影响」。写“更准确”“更完整”时必须跟可验证的事实；拿不出事实就删去评价。按实际影响而非缺点条数裁决，不为赢家删问题或为输家凑问题；同一缺陷不拆成多条，不把篇幅、工具次数、引用数当作质量。来源链接、脚注编号和引用格式等展示瑕疵默认 low，不单凭这些判核心未完成或决定输赢；缺少来源不等于事实错误。有证据的伪造来源或关键引文矛盾实质影响核心事实时才提高重要性，用户明确要求可追溯来源时评估具体未交付项。

先理解用户实际需要，再以共同要求比较双方。历史上下文只帮助理解约束和指代。对不确定的事实明确保留不确定性，不把它升级成决定胜负的错误。

数值对错先统一单位、日期和统计口径；有明确容差或区间时遵循题目/标准，否则按标准展示的末位精度四舍五入后比较。“约/≈”不授权自行放宽百分比误差。标准与工具数据冲突时区分“不符合标准”与“模型计算错误”，无法证实上游原因时保留不确定性。同一精度规则适用于所有组别。

双方同样的缺陷使用同样标准；发现重大反向证据时解释为什么它改变或没有改变结论。先判断结果，再分别审视完成耗时和 token 用量：前者是等待，后者是资源消耗。有实质差异才写进逐项对比，裁决短评只保留影响取舍的指标；不把每题都写成时间比较。更多 token 是否补齐了结果、排除了错误候选或只是重复查询，要依据调用链和交付说明；无法核实消耗原因时不猜测。相同质量下显著更少的 token 是资源效率优势，即使耗时接近也应考虑。指标缺失、冲突或不可比不补零、不估算；缓存不再次加到总量，未知定价不推断费用，不因分词与计数口径的小差异判高下，单样本不推出长期性能。首段可能只是过程说明，只有 trace 的内容与时间能逐条对应时才能判断中途交付，不能将首段时刻贴到最终答案上。Workflow 提供全部既有优点的双向核对清单；每个比较项都检查对方同一能力，确认没做到就明确写出对应的相对短板与影响，反向优势也逐项对应；共同优点合并，未知保留未知，独立优点不能漏掉。不能用 A 的引用对比 B 的文风，也不能把缺少同名 finding 当作缺少能力；相对短板不新增归因 finding，不把可选加分项缺失变成核心错误。

改写阶段只润色表达：正式结果 JSONL 保留裁判被接受时的原文，源结果的 `rewritten` 字段保存短评，报告与逐题总结优先展示后者。点评开门见山，以具体事实点出关键得失，用通俗易懂的短句写清必要原因和影响，不做同义词替换式润色；删除“因此不能判定为正确”这类重复判词，但保留“疑似”“无法核实”等真实不确定性；保留理解结论所需的信息，删去抽象套话、裁判自评打分及无关置信度分档（如“6/10 置信度”），不要把遵守用户指令当成果。复核以正式结果为准；改写使用真实组别与模型称谓，不改事实、保留下来的数字或不确定性，也不能新增结论；都差时保留原裁决已确定的相对优劣及理由、影响取舍的反向优势，不能只写共同失败，也不能根据逐项表现自行选优；默认开启归因、对比和聚类改写；其中普通对比默认改写偏好理由，自动化还必须改写每个逐项点评，也可显式刷新指定槽位，材料和槽位边界见[改写契约](contract.md#改写)；不得新增这些材料没有的数字，格式化千位分隔符不算数值变化；可删去不支撑判断的指标枚举，不能删掉独立优点与另一方短板的对应关系。提示词只能引导文风，真实模型的表达质量仍须抽样复核。

归因沿最终结论、工具返回和调用参数追溯可证实的出错环节。component 是责任组件数组；工具正确执行错误请求或模型误读正确返回时归模型，工具返回本身有缺陷并传入错误结论时归工具，双方均有独立证据才共同列入。每个工具都要有自己的调用/返回证据，definition 逐个解释责任；工具出现过、没返回数据，不足以证明它有责任。最终数字可能来自其他搜索，必须继续追查；找不到来源就保留不确定性。多组件共用一条 finding，聚类按组件分别记录关联，不重复计算回答缺点。责任未查明时 component=[]，definition 保留实际工具来源与待查原因，看板显示“待定位”；已确认的结果偏差仍可保持 established。被评模型不可见标准答案，不能以未核对标准值归责模型。未定位组件的 finding 保留在归因和对比中，暂不进入按组件组织的问题库。正常返回二手资料本身不构成工具缺陷；被后续有效材料补齐的偶发失败不算结果缺陷。标准数值精度不同时逐项核算，并查看全部表格列，区分主推口径选错与正确值完全缺失。

聚类阶段只做问题归类：归因给出的 `component/label/definition` 是原始描述，同一组件下同一现象的不同说法应归入同一类，不跨工具组件归类或合并；新增类受单次预算和每模型上限约束，必要时合并近义类。疑似问题也归类，但在观察示例及问题库出现样本中保留 `evidence_status=uncertain`，不能作为已确认缺陷叙述。复核时以问题库的类定义和出现样本为准，不把措辞差异当作新问题。

## 简短示例

以下为虚构的表达示例，只展示写法，不提供可套用的事实或判决。

| 空泛写法 | 可核对的写法 |
|---|---|
| “A 更完整。” | “用户要求五条记录。A 提供全部五条，B 只提供两条且未解释缺失，因此 A 完成了所需交付。” |
| “B 更严谨。” | “A 将 0.9957% 四舍五入为 0.10%；B 给出 1.00%。该差异改变核心数值结论，因此 B 更可靠。” |
| “双方各有优劣。” | “双方结果相同且均可核验；A 解释简洁，B 多给了一种核算方法，均满足核心要求且无实质差异，因此都好。” |
| “双方都不太行。” | “题目要求计算 2+2，双方均给出 5，核心交付都错误且无其他可用性差异，因此都差。” |
| “A 给了代码，所以判 A 胜。” | “双方都差：都没给实际回测结果。A相对更好，给出可执行代码，B只有方法介绍，但仍未完成结果交付。” |

聚类通过请求内 C/O 短编号引用问题类和观察，由程序还原真实身份；模型不承担逐字抄写 UUID 的工作。短编号只解决引用可靠性，不证明归类语义正确。

裁判提交的 findings 使用材料工具提供的 `evidence_id`，Host 展开为正式结果中的消息序号和逐字引文；不要求裁判手写引文。详细结论不应以内部工具调试过程代替用户关心的实际影响。

## 可校验的数值与实体对应

字段、证据硬校验和独立复核流程以[数值与实体核验](contract.md#数值与实体核验)为准。语义验收重点是标准与回答的对象、单位和数值方向是否一致，以及最终实体表与全部可比来源是否对应；检查裁短引文、表头单位或后续加工是否掩盖反证。来源缺失和截断不能直接当作答案错误，确实未知的结果应保留待复核。

这项机械核验限于可识别代码/名称表头及可比来源，不覆盖任意自然语言事实、所有别名或全部表格格式。来源独立性、时间范围、复合加工与判词影响仍须语义核查；晚出现的加工表不能掩盖更早来源的冲突。

固定受控正反例见 [evaluation-quality.json](../tests/fixtures/evaluation-quality.json)，覆盖量纲、符号、实体错配及截断来源防误判；这些预期是受控变体检查，不冒充人工金标。真实复评须分别记录原位和 A/B 换位结果、漏判、误判、待复核与未完成数，执行成功率单独报告。

## 真实模型复核

自动测试检查结构、映射、引用和故障处理；模拟网关不证明模型事实判断正确。修改提示词、模型或关键预算时：

1. 固定小题集，覆盖有/无标准答案、多轮上下文、数值差异、工具引用与图片，以及双方达标、双方核心失败、双方有错但一方仍明显更优、材料不足；记录输入 UUID、业务标识、模型、底座、契约和预算。
2. 两个底座使用相同题集。人工核查决定性发现、影响与反向证据，记录人工判断及分歧原因。
3. 使用显式 A/B 位置交换，检查稳定版本映射与判决一致性。
4. 在独立输入目录构造只改变一个关键事实的变体，使用新 run ID 重新执行归因和对比阶段，复核结论是否合理响应。不要修改固定回归集引用的源文件；同 run ID 会保留已接受结果，不能用来验证事实变更后的重评效果。
5. 研究裁判稳定性时使用独立 run ID，至少重复三次，记录分歧、用量、耗时及未完成率。

先处理 preflight 输入问题。缺少最终回答的记录应跳过，不能算作都差。人工复核记录随该次实验保存在 `data/runs/comparison/`，不追加到本指南。

## 改写放量验收

[固定对照题集](../packages/agents/src/rewrite/fixtures/quality.json)保存样例：真实返工的“未展示→未核查”、主体标签串位、辅助标签混入、偏好遗漏，局部优势、并列、相反系统要求、对照方数字串入，以及都差时保留相对优劣、不得反转或自创偏好、不能改成胜出和无差距不硬选。每题标记真实来源或受控变体，并给出可接受表达、拒绝表达和复核理由。带 `error_code` 的反例由[回归测试](../packages/agents/src/rewrite/quality.test.ts)机械拦截；其余反例是语义复核标准，测试通过不能证明它们已经被程序识别。相反系统提示的完整材料测试仍在[工作流集成回归](../tests/integration/host/optimization.test.ts)。

一次放量遵循以下门槛：

1. 新日期 run 先用 `--pilot-cases 30` 或40选分层小批，本地配置先设较低并发。确认各日期/组别覆盖；再从实际样本中补查上述语义边界，不能把日期分层当成语义分层。
2. 对本轮要求运行 `validate --selected --require-rewrite verdicts`；逐项点评也必需时，先按[使用指南](usage.md#重新改写对比文案)准备并完成这些槽位，再增加 `--require-rewrite items`。查看 `results`、`evidence`、`rewrites` 和 `delivery` 四部分，历史例外逐条记录。
3. `rewrite-review` 输出每场所有格的原文、只读对照、既定偏好和改写；结合固定题集检查完整的一场。主体串位、偏好反转、事实或确定性扩大任意出现一次，本阶段不能放量；先定位材料、提示或校验问题，再只刷新问题槽位。评价文风时要求具体得失、准确主语和必要限定，不以“更狠”代替信息。
4. 确认通过后用同 run 的 `--discover-inputs` 放开余下任务。逐级提高并发，记录连续两个观察窗口的 comparison/rewrite 接受数、同类错误与返工量；如果净产出未提升或错误明显增多，先降并发诊断。窗口可从一分钟起步，长任务应扩大窗口以避免样本不足。
5. 全量完成后不带 `--selected` 验收，明确日期集合和所需槽位。程序只证明机械约束与覆盖，不能把 `semantic_review: required` 写成“全量语义已通过”。

结构或证据的确定性错误先加最小回归再修代码；数字改写与不确定性的普遍判断仍需语义检查，不新增宽泛关键词黑名单。熔断不是语义裁判，也不会因为一份JSON通过就自动升并发。

## 离线回归与小样本入口

先运行 `npm run build:app`。`collect` 从 debug 运行的事件日志中收集 `submit_evaluation` 直接提交被拒绝时的草稿；普通运行中仅保存在状态里的草稿、`submit_evaluation_file` 的失败不会被收集。下面的 `pi-debug` 应是已通过 `--debug` 留存这类事件的运行。

回归集严格保留当前原始草稿，不转换旧证据格式或补造 finding ID；使用 `eval-offline-fixtures` 格式，过期材料重新 collect。回归集拒绝覆盖，使用新路径建立。

```bash
npm run benchmark -- collect --run data/runs/comparison/pi-debug --output .artifacts/regression/fixtures.json --limit 32
npm run benchmark -- replay --fixtures .artifacts/regression/fixtures.json --output .artifacts/regression/replay.json
npm run benchmark -- run --fixtures .artifacts/regression/fixtures.json --run-id sample-pi --limit 4
```

回归集保存固定草稿、预期结果和原始输入引用，不嵌入输入副本。源文件记录与业务标识不一致时回放明确报错，避免把新材料用于旧草稿。

`run` 默认仅预览；只有显式增加 `--execute` 才调用真实模型。可选 `--engine prime`，`--swap` 交换相同小样本的 A/B 分配；真实运行默认输出到 `.artifacts/model-benchmarks/`，要求新 run ID。`--limit` 在 `collect` 中限制草稿条数，在 `run` 中限制对比组数；归因依赖另行执行。统计保存在 `stats.json`，口径见[运行产物](usage.md#运行产物)。回归集中的失败草稿不是全量提交样本，不能用来计算生产运行的首次通过率。

完成原始位置和 `--swap` 的两次真实运行后，才可比较其结果目录：

```bash
npm run benchmark -- compare --run .artifacts/model-benchmarks/sample-pi --run .artifacts/model-benchmarks/sample-pi-swapped --output .artifacts/regression/stability.json
```

`compare` 按业务 case 与稳定模型对读取当前 `comparison.jsonl.verdicts`，比较缺失、outcome、winner、核心分类和决定依据，并关联 evaluator/judge 收据；文本变化单列，输出理由和决定性引用供人工抽查。离线通过只说明机械契约与证据定位行为一致，不能代替真实模型质量及交换稳定性复核。

数值核对、偏好前缀和改写槽位的机械约束以[数值与实体核验](contract.md#数值与实体核验)和[改写契约](contract.md#改写)为准。离线回放只验证当前规则是否一致，数值对象是否抽对、相对偏好是否保真、数字与语气是否扩大，仍需按上面的[真实模型复核](#真实模型复核)检查。

## 数值表示与超长最终回答材料

数值核对支持原文的科学计数法，expected 保留尾数小数位和指数。例如 `1.13018E+12` 的末位精度为千万位，不能展开为整数后改按个位判错；exact 模式仍要求数值完全相等。区间连接符不误当负号，日期标签后紧跟的负数（如 `2020年-0.09854252`）仍保留符号。带空格的正负号与明确“下降/净流出”的方向也纳入核验；显式负数不能当作正数。actual 照抄原文数值，单位换算只填 scale，不能先换算 actual 再声称它来自原文。复合单位、分数、列表计数、图表解码等派生量在 correctness_reason 中保留原文证据与计算过程，不伪装为逐字数值。已接受结果不因校验规则变化而重评。

最终回答中超过首屏预算（最低 16000 字符）的单个文本块不在初始正文和证据中重复展开，而以 `deferred_final_material` 给出消息、路径和完整长度；块前后的短正文仍完整展示。原始输入与证据坐标保持不变，评审须用工具补读，图表编码数据可从输入文件解析。已接受结果不因材料呈现变化而重评。

## 矩阵、区间与人工金标

```bash
npm run benchmark -- summarize --run data/runs/comparison/RUN --bootstrap-rounds 2000
npm run benchmark -- gold-template --run data/runs/comparison/RUN --output .artifacts/expert.json
npm run benchmark -- calibrate --run data/runs/comparison/RUN --gold .artifacts/expert.json
```

矩阵按实际模型对列出胜负、都好、都差；统计分数沿用 gate 口径（胜1、负0、都好/都差0.5），不解释为人类偏好或 Arena 的 BT 排名。区间按业务 case 成簇 bootstrap，保留同题多场对局的相关性；单 case、无观测变异或有效重采样不足不出伪确定区间。混合 evaluator/judge 与上游归因来源分别列 cohort，缺失和待复核不当平局。

金标模板只提供业务定位，判定留空，`reviewed=false`。专家填写 reviewer、rationale、各模型核心分类、outcome 与 winner，再明确 `reviewed=true`；校准只统计这些人工确认条目，分别报告核心分类、outcome、winner 一致率、缺失和错判。模板与结构测试不是语义验收；实际模型与专家一致性须用人工审定样本验证。

超长最终材料逐块要求实际 read/search 返回覆盖全部字符，按原始 UTF-16 半开坐标合并；检索范围、JSON 扫描或未返回页不算已阅读正文。最终图片必须实际 view_image。换位实验比较同一业务模型对，不能把不同 case 当位置偏差。
