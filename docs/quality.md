# 评测质量

[返回首页](../README.md) · 机器可校验的结构和证据规则见[数据契约](contract.md)。

## 评语标准

结论先回答谁更好、为何都好或为何都差，再解释足以改变结论的事实。按[判决契约](contract.md#阶段与判决)先判断核心任务完成情况，再判断差异的实际影响。双方达标且可用性相当时判都好；双方核心任务失败且局部优点不足以区分胜负时判都差。判赢家时，说明用户采用该回答会在哪项核心结果上获益。

每条评价都应串起「具体观察 → 可核对证据 → 判断依据 → 对用户的影响」。写“更准确”“更完整”时必须跟可验证的事实；拿不出事实就删去评价。不要凑固定数量的优缺点，不把篇幅、工具次数、引用数当作质量。

先理解用户实际需要，再以共同要求比较双方。历史上下文只帮助理解约束和指代。对不确定的事实明确保留不确定性，不把它升级成决定胜负的错误。

双方同样的缺陷使用同样标准；发现重大反向证据时解释为什么它改变或没有改变结论。原始回答耗时有完整数据才比较，没有数据时不补零、不猜测，也不填充无意义说明。

## 简短示例

以下为虚构的表达示例，只展示写法，不提供可套用的事实或判决。

| 空泛写法 | 可核对的写法 |
|---|---|
| “A 更完整。” | “用户要求五条记录。A 提供全部五条，B 只提供两条且未解释缺失，因此 A 完成了所需交付。” |
| “B 更严谨。” | “A 将 0.9957% 四舍五入为 0.10%；B 给出 1.00%。该差异改变核心数值结论，因此 B 更可靠。” |
| “双方各有优劣。” | “双方结果相同且均可核验；A 解释简洁，B 多给了一种核算方法，均满足核心要求且无实质差异，因此都好。” |
| “双方都不太行。” | “题目要求计算 2+2，双方均给出 5，核心交付都错误且无其他可用性差异，因此都差。” |
| “A 的框架更完整，所以 A 更好。” | “用户要实际回测结果。双方均未运行回测，A 多写的方法说明仍未完成核心交付，因此都差。” |

正式 findings 还要附当前输入中的消息序号和逐字引文。详细结论不应以内部工具调试过程代替用户关心的实际影响。

## 真实模型复核

自动测试检查结构、映射、引用和故障处理；模拟网关不证明模型事实判断正确。修改提示词、模型或关键预算时：

1. 固定小题集，覆盖有/无标准答案、多轮上下文、数值差异、工具引用与图片，以及双方达标、双方核心失败、双方有错但一方仍明显更优、材料不足；记录输入哈希、模型、底座、契约和预算。
2. 两个底座使用相同题集。人工核查决定性发现、影响与反向证据，记录人工判断及分歧原因。
3. 改变盲测种子测试 A/B 位置交换，检查稳定版本映射与判决一致性。
4. 改变一个关键事实，确认缓存失效并复核结论是否合理响应。
5. 检查相同配置的缓存行为；研究裁判稳定性时使用独立 `cacheDir`，至少重复三次，记录分歧、用量、耗时及未完成率。

先处理 preflight 输入问题。缺少最终回答的记录应跳过，不能算作都差。人工复核记录随该次实验保存在 `data/runs/`，不追加到本指南。
